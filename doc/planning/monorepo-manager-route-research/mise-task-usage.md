### Naming and the implicit dependency graph

Verified (`mise.toml:624-625`):

```text
# Task naming follows `${category}${optional(`--${modifier}`)}:${child}`
# never use depends or post depends, use run only because it's the easiest to understand.
```

Verified (`analyze.ts`):

- 208 distinct leaf names.
   Instances by colon depth:
   478 at depth 1,
   979 at depth 2,
   261 at depth 3,
   118 at depth 4.
- The `--modifier` half of the stated convention is used exactly once,
   by `//:prepareAndBuild--allowFailure` (`mise.toml:1091`).

The colon hierarchy is not decoration.
Verified (`mise.toml:291-307`):
`vars.fanout` reads `MISE_TASK_NAME`,
enumerates `mise tasks --all --hidden --json`,
keeps names one colon level deeper,
and spawns `mise run <child>` for each.
So `build` runs whatever is named `build:*`,
and a task's position in the graph is decided by its name.

## 2. The good

### Templates plus discovery give one vocabulary across 179 packages

Verified:
`mise run //package/<anything>:lint:types` works
for all 145 packages that declare it,
with one definition at `mise.toml:606-612`.
An agent or a person never has to read a package
to know how to type-check it.
`AGENTS.md:887` depends on exactly this
when it tells agents to run `mise run //package/<path>:test:unit`.

This is the property meow must not lose.
It is worth more than the boilerplate it costs.

### Bazel-shaped labels, already in muscle memory

Verified:
1836 of 1836 tasks carry a `//path:task` label,
and `mise task info '//:lint'` resolves one.
The design's "Follow Bazel" target syntax
is not a new convention for this repository;
it is the one already in use.

### Standing in a package narrows what you see

Verified (`mise tasks --json` from `package/jsonc-edit/core-ts`):
56 tasks,
the 41 visible root tasks plus that package's 15.
No sibling noise.
This is a real affordance,
and it comes entirely from file placement.

### The working directory is derived, not declared

Verified:
174 distinct `dir` values across 1836 tasks,
but only 35 explicit `dir =` lines.
Nearly every task gets the right cwd
because of where its file sits.
`cargo nextest run` in `package/linter/rust/mise.toml`
needs no path at all.

### The Node shell is a deliberate, measured choice

Verified (`doc/decision/mise-task-node-invocations.md`):
the alternative was benchmarked
(spawn 56.9 ms against import 37.3 ms at the node level,
190.0 ms against 173.5 ms at the mise level,
with a real `lint:oxlint` at 466 ms)
and rejected on fragility grounds,
not on taste.
Rule `SCR` then encodes it.
The repository writes no shell scripts,
which removes an entire class of quoting bug.

### Generated root configuration keeps a hand-editable source

Verified (`mise.toml:1`,
 `file-enforcer.config.ts:718-723`):
`mise.no-env.toml` is the file a person edits;
the machine-derived `[env]` block is appended.
The seam is clean,
and `AGENTS.md:899-903` states it.

### Backend disabling is justified in place

Verified (`mise.toml:226-241`).
Each disabled backend carries its reason in a `#region` comment.
This is the layer-5 pattern that signals discipline rather than debt.

## 3. The bad

### Seven of every ten task blocks written here are boilerplate

Verified (`files.ts`):
1,341 of 1,898 task blocks are a bare `extends`.
Counting header plus body,
2,632 of the 8,463 lines under `package/**` exist
only to opt a package into a template it could have been selected for.

Concretely,
`package/jsonc-edit/core-ts/mise.toml` opens with 13 consecutive blocks
of the form:

```toml
[tasks."build:js:browser"]
extends = "build:js:browser"
```

Adding a package means copying that block.
Adding a template means editing up to 143 files.

### `buildAndTest` is the same two lines, 47 times

Verified (`odd.ts` over the task dump):
56 tasks are named `buildAndTest`,
with 6 distinct bodies,
and 47 of them are byte-identical:

```toml
run = ["mise run build", "mise run test:unit"]
```

There is no `task_templates.buildAndTest`
(`rg --line-number '^\[task_templates' mise.toml` lists 19 templates,
 not including it).
The most duplicated task in the repository is the one template nobody wrote.

### Each package repeats its description, or has none

Verified:
827 of 1836 tasks have no description.
The 1009 that do include 143 copies of "Lint with Oxlint"
inherited from one template,
alongside genuinely package-specific text.
`mise tasks` output is therefore a mix of one sentence repeated
and long tails of silence.

### The stated `depends` ban is broken 41 times, quietly

Verified:
`mise.toml:625` forbids `depends`;
41 tasks use it.
The uses are not frivolous:
12 are `//package/pi-plugin/*:verify:extension` depending on `build`,
5 are oxlint plugins whose `test:unit` depends on `build`,
6 are `//package/music-player/android-app:*` depending on `build:native`.
Every one expresses a real build-before-test edge
that `run = ["mise run build", ...]` would express worse
by spawning another `mise` process.
The policy lost,
and no document records that it lost.

### The two ordering mechanisms coexist with no rule

Verified:
6 tasks use Mise's native `{ tasks = [...] }` run entries,
including `//:lint` (`mise.toml:858-861`)
and `//:format`.
Verified (`mise.toml:285`):
the `fanout` comment says
"No `:::` separator or other mise-specific inline sugar."
So the root config both avoids Mise task sugar in its fan-out helper
and uses Mise task sugar two hundred lines later.
Nothing states when each applies.

### `usage` is effectively one template's feature

Verified:
135 tasks declare `usage`,
and 102 of those inherit it from `test:unit`.
Only 33 hand-written usage specs exist across 179 packages.
Verified (`doc/decision/mise-task-node-invocations.md`):
declaring `usage` changes argument delivery,
from an appended argv vector to `usage_*` environment variables,
which is why 116 run lines must interpolate `{{vars.parse_usage_args}}`
to undo the encoding.
The feature is avoided because using it costs a parser.

### Nothing is cached, so the aggregates are slow by construction

Verified:
zero tasks declare `sources` or `outputs`.
Verified (`hyperfine --warmup 1 --runs 5 'mise tasks --all --hidden --json'`):
223.3 ms plus or minus 8.2 ms per enumeration.
Verified (`mise.toml:291-307`,
 `:322-347`):
every fan-out task pays that enumeration once.
Verified (`doc/decision/mise-task-node-invocations.md`):
Mise process startup is about 135 ms.

Inference,
not measured end to end:
`mise run lint` enumerates once,
then spawns one `mise run` per matching package.
Verified:
166 package tasks are named `lint`,
141 of which extend the fan-out template and therefore enumerate again.
So one `mise run lint` performs at least 142 enumerations,
about 32 seconds at the measured 223 ms,
and starts at least 167 `mise` processes,
about 23 seconds at the 135 ms figure in the decision record,
before any linter runs.
Rule `QAB` applies:
this is arithmetic over measured components,
not an observed wall clock,
and running the real aggregate was out of scope for this study.

### Short flags in configuration, against rule `LFF`

Verified:
`mise watch -w src -r -- ...` appears in
`package/kwin/key-helper/mise.toml:40`,
`package/hall-monitor/daemon/mise.toml:11`,
`package/rss/app/mise.toml:21`,

## 4. The ugly

### A task's real body is invisible from both its definition and `mise task info`

Verified:
1,159 of 1,836 tasks (63.1 percent) have a `run` containing `{{vars.`.
Verified (`mise task info '//package/jsonc-edit/core-ts:lint:oxlint'`):

```text
Run:
  {{vars.dispatch_workspace_node}}
  ensureOxlintConfig()
  runWorkspaceNode('package/monorepo-task/core-exec', 'oxlint-wrapper', [])
```

The inspection command prints the template,
unexpanded.
To learn what `//package/jsonc-edit/core-ts:lint:oxlint` does,
a reader must open `mise.toml`,
find `[task_templates."lint:oxlint"]` at line 590,
then read `vars.dispatch_workspace_node` at lines 358 to 420,
a 62-line function that resolves the monorepo root,
chooses built output over source,
walks two package directories,
compares mtimes,
and may spawn `mise run //package/config/oxlint:build:js:node`.
None of that is reachable from the target name.

This is the finding that most directly justifies meow.

## 5. What meow's decided design fixes, keeps, or breaks

Decisions read from
`doc/planning/monorepo-manager-from-scratch-design.md`
"Configuration authoring" (`:1627-1696`),
"Consequences of one root file" (`:1697-1711`),
"User interface" (`:169-477`),
"Declarative configuration" (`:1466-1626`),
"HCL tooling" (`:1712-1884`).

The design document was edited by concurrent work during this study,
growing from 3,175 to 3,196 lines.
Line citations are against the 3,196-line state read on 2026-09-17.
Rule `EC1`:
nothing was touched.

### Fixed outright

Tags instead of file placement
removes 2,632 lines under `package/**`:
1,316 blocks whose entire content is a header plus one `extends` line.
A package that is a TypeScript library gets `lint:types`
because it is a TypeScript library,
not because someone pasted a block.
This is the largest single measured win available.

Most-specific-tag-wins with explicit override markers
addresses the 96 silent shadows and the 21 partial overrides directly.
Verified (`:1664-1694`):
the markers are the paired meta-arguments
`overridden = true` on the base and `override = true` on the specialization,
"validated as a pair".
`package/wg/cli-quicker-exempt:test:unit` running `cargo test`
becomes a marked override of a marked-overridable base,
or an error.
The dead `extends` at
`package/oxlint-plugin/no-restricted-syntax/mise.toml:8`
becomes detectable,
because a specialization with no marked base is an error.

A real expression language ends the textual interpolation hazard.
`vars.fanout` and friends are not values;
they are source fragments pasted into a module scope,
which is what produced
`doc/troubleshooting/mise-inline-task-import-collision.md`
and the ordering rule at `mise.toml:490-494`.
HCL values compose;
string fragments do not.

`meow watch` keeping everything up to date,
plus a content-addressed cache,
answers the zero-`sources`,
 zero-`outputs`,
 223-ms-per-enumeration finding.
The 142-enumeration arithmetic for one `mise run lint` disappears
when there is one resident process holding the graph.

`meow status` showing failed,
 paused,
 blocked,
 flaky,
 queued,
 and running
replaces `//:lint`'s current behavior of printing one aggregated error string
listing failed package names
(`mise.toml:346`).

Rule `SYB` and the argv-list command shape
remove the 26 `;`-separated and 112 `&&`-chained run entries
and the hand-written shell-word parser at `mise.toml:426-451`.

### Kept, and worth keeping deliberately

Bazel-shaped labels are already the repository's vocabulary:
1836 of 1836 tasks carry one.
`meow run //package/cow:test` will read as familiar,
not as migration cost.

Glob targets with shell-quoting diagnostics
match how people already reach for `//package/...`,
including at `doc/decision/desktop-app-podman-build.md:86`.

Byte-exact output forwarding for a single target
matches today's `stdio: 'inherit'` throughout the fan-out helpers.

The one root file is not the break it looks like for tools or environment.
Verified:
package configuration files contain only `[tasks.*]`,
five `[vars]`,
and three `[env]`.
There is no per-package tool pinning and no per-package settings to relocate.

### Made worse, or left unanswered

#### The one root file removes the relevance filter, and nothing replaces it

Verified:
from `package/jsonc-edit/core-ts`,
`mise tasks` lists 56 tasks:
41 root plus that package's 15.
The design settles target labels
("they come from the package a tag selected",
 `:1698-1701`)
but says nothing about what a person or agent sees
when they are standing in a directory and ask what they can run.
With no per-package file,
directory context no longer narrows anything by construction.

Today this affordance is what makes `AGENTS.md:891` workable:
"Read root + package `mise.toml` for available commands."
That instruction has no meow equivalent.

#### The one root file is large, and the estimate should be on the record

Verified:
removing every bare-extends block leaves 5,831 substantive lines under `package/**`,
plus 1,240 lines of hand-maintained root source.
So a single `meow.hcl` expressing today's content
lands near 7,000 lines before any HCL syntax overhead.
The design acknowledges "The file is large by construction" (`:1708-1711`)
but does not name a number.
7,000 lines is past the point where
`hcl-edit`'s missing formatter (`:1544-1548`)
and the language server's outline become load-bearing rather than nice.

#### Argv-only commands have no home for 1,155 lines of logic

The design states:
"A task's command is an argv list,
spawned directly with no shell:
`command = ["node", "--test", "src"]`" (`:1642-1646`).

Verified:
1,215 tasks currently declare a Node shell,
1,159 interpolate a `vars` fragment,
and 1,155 lines of TypeScript live inside triple-quoted strings.
Much of that logic is not decoration:
`dispatch_workspace_node` chooses built output over source,
`run_test_files` finds each test file's package root,
`fanout_packages` bounds concurrency by `availableParallelism()`.

Under meow those responsibilities move.
Concurrency bounding and fan-out become the daemon's job,
which is decided.
Built-versus-source selection and test discovery do not have an owner yet.
The design's logic inventory (`:1488-1520`) counts
`file-enforcer.config.ts` units,
not these.
Rule `RCO` asks for a coverage ledger before removing an incumbent,
and these lines are not in one.

#### Tag inference must reproduce a graph that is currently encoded in names

Verified (`mise.toml:291-307`):
`fanout` selects children by counting colons in the task name.
Verified (`package/kwin/key-helper/mise.toml:42-43`):

```text

# subtask, does not pull it in before the ESM bundle exists.
```

A task was renamed to change what runs.
Verified (`package/linter/kotlin/mise.toml:1-4`) records the mirror case:
the whole-tree scan lives at the root
"so the fanout-discovered package `lint` below stays a local compile check
and does not scan the repo twice."

Tag-based selection is a better model than name-prefix selection,
but these two comments are the only places the current graph's exceptions are written down.
Migration has to find the rest,
and there is no list.

#### Explicit override markers meet a tree with 41 unmarked `depends` edges and a ban on them

Verified:
`mise.toml:625` bans `depends`;
41 tasks use it;
the coverage ledger at
`doc/planning/mise-removal-coverage.md:86-92` records
"no cross-package build dependency is declared."
Verified:
that is not quite right today.
`package/test-harness/core/mise.toml:7` declares
`depends = ["//package/test-harness/core:build:js:node", "//package/test-harness/core:build:js:client"]`,

All 41 are intra-package.

The design settles ordering from
"declared reads,
 writes,
 and explicit `depends_on`" (`:1559-1562`).
That is a third model,
neither today's name-prefix fan-out nor today's `depends`.
Nothing yet maps the 41 edges onto it,
and the repository's own stated policy about them is stale.

#### Nothing in the design covers the run-time reality that broke things here

Three findings have no counterpart in the decided design,
and each cost this repository a troubleshooting document:

- Windows command variants.
   Verified:
   5 `run_windows` lines,

## 6. Questions for the user

Rule `QGR`:
everything settled requirements already determine has been left out.
Four questions remain,
each turning on preference or authority rather than measurement.

### Question 1: what replaces standing in a directory?

Today,
 `mise tasks` inside `package/jsonc-edit/core-ts` shows 56 tasks
instead of 1807.
One root `meow.hcl` removes the mechanism that produces that.

Option A,
 `meow` infers the package from the process working directory
and narrows listings and relative targets to it.

- Pros:
   preserves today's affordance exactly;
   keeps `AGENTS.md:891` meaningful with a wording change;
   matches the design's existing "relative forms" target syntax (`:288-297`).
- Cons:
   adds hidden state to every command;
   two terminals in different directories behave differently,
   which the JSON stream will not explain.

Option B,
 no directory inference;
narrowing is explicit,
for example `meow status //package/module/...`.

- Pros:
   one command means one thing everywhere;
   simplest to specify and to log.
- Cons:
   every listing starts from 1800-plus targets;
   loses an affordance that costs nothing today.

Option C,
 directory inference for listing and status only,
never for `meow run`.

- Pros:
   the destructive path stays explicit while the exploratory path stays convenient;
   a wrong guess can only mislist,
   never misrun.
- Cons:
   a split rule to learn;
   the design currently describes one target grammar,
   not two.

Ranking:
 C > A > B.
C over A because the only real hazard in directory inference
is running the wrong package's task,
and C removes exactly that while keeping the benefit.
A over B because B discards a measured affordance
(56 versus 1807) to buy consistency that C already buys.

### Question 2: where does per-task logic live when commands are argv lists?

1,155 lines of TypeScript currently sit in task bodies.
Fan-out and concurrency go to the daemon.
Built-versus-source selection,
test-file discovery,
and platform branching do not have an owner.

Option A,
 repository packages with real `bin` entries,
invoked as `command = ["node", "package/monorepo-task/core-exec/src/dispatch.ts", ...]`.

- Pros:
   the code becomes lintable,
   type-checked,
   and testable,
   which today it is not;
   rule `RCI` prefers extending `task-util`,
   which already owns this boundary;
   no meow feature needed.
- Cons:
   pays a Node start per dispatch,
   already measured at 56.9 ms in
   `doc/decision/mise-task-node-invocations.md`;
   keeps a Node dependency on paths meow could own.

Option B,
 meow built-ins for the recurring cases
(prefer-built-output,
 discover-test-files).

- Pros:
   removes the Node hop entirely;
   the daemon can cache the discovery;
   the behavior becomes inspectable from the target.
- Cons:
   meow grows repository-specific features;
   each built-in is a new thing to specify,
   build,
   and document
   before meow can replace Mise at all.

Option C,
 HCL expressions in `meow.hcl`,
using the evaluator to pick paths and expand file lists.

- Pros:
   stays in one language;
   matches the "full language allowed" answer (`:1573`).
- Cons:
   puts filesystem probing in configuration evaluation,
   which the design wants cacheable by read set;
   `hcl-rs` has no built-in functions (issue #484,
   noted at `:1544-1545`).

Ranking:
 A > B > C.
A over B because A needs no meow feature and makes 1,155 currently unchecked lines
subject to the repository's own TypeScript rules,
which is a correctness win available immediately.
B over C because C makes configuration evaluation do I/O,
which conflicts with the cache-key design the same document settles.

### Question 3: does the `depends` ban survive?

`mise.toml:625` bans `depends`;
41 tasks use it;
the design settles ordering from declared reads,
 writes,
 and `depends_on`.

Option A,
 retire the ban.
meow gets `depends_on`,
and the 41 edges migrate as-is.

- Pros:
   matches the design already settled at `:1559-1562`;
   matches what the tree does;
   ends a policy that is provably not enforced.
- Cons:
   loses whatever readability the ban was buying;
   `AGENTS.md` and the root comment both need editing.

Option B,
 keep the ban,
and require every edge to be expressed as reads and writes
so meow infers the order.

- Pros:
   maximal caching,
   since a declared write is also a cache input;
   no author ever states an order that the file set contradicts.
- Cons:
   12 `pi-plugin` `verify:extension` tasks depend on `build`
   for reasons that are about artifact existence,
   not file contents;
   forcing every edge through file declarations may be more ceremony than the ban saved.

Ranking:
 A > B.
A over B because the ban's stated reason,
"it's the easiest to understand",
is already contradicted by 41 counterexamples,
and B asks authors to encode an artifact-existence edge as a file-set edge,
which is the harder thing to read,
not the easier one.

### Question 4: how does an agent in a disposable worktree get past the trust prompt?

Rule `IWT` requires decision-verb work to happen in `git worktree add` forks.
Verified (`doc/troubleshooting/mise-disposable-worktree-trust.md`):
Mise already blocks there today.
meow's trust model prints every evaluated file and waits for an answer (`:389-418`).
An agent cannot answer it.

Option A,
 trust follows repository identity,
so a worktree of an already-trusted repository at the same commit inherits trust.

- Pros:
   the worktree case disappears;
   `cli-git` already reasons about repository identity,
   which rule `WXG` and `doc/planning/git-wrong-repository-identity-defense.md` cover.
- Cons:
   a worktree can be checked out at an untrusted commit;
   identity is a weaker key than exact bytes,
   which the design chose deliberately.

Option B,
 a `meow trust --accept-file <path>` non-interactive form
that a caller may use only when it already holds the bytes.

- Pros:
   keeps exact-bytes trust intact;
   scriptable,
   so `IWT` workflows and CI both work.
- Cons:
   an agent that can call it has effectively self-trusted;
   the security property becomes a convention about who may call it.

Option C,
 leave it interactive and require the human to trust each worktree.

- Pros:
   strongest property,
   no new surface.
- Cons:
   every decision-verb task now needs a human in the loop for setup,
   which rule `CB1` says to bridge rather than hand off.

Ranking:
 B > A > C.
B over A because A silently weakens the exact-bytes rule the design settled,
while B keeps it and moves the decision to an explicit,
 auditable call.
A over C because C makes the repository's own mandated workflow
require a human for every fork,
which is a cost paid constantly for a risk that arises rarely.
