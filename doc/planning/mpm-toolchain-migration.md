# MPM toolchain migration implementation spec

Status:
 implementation plan for `doc/decision/mpm-toolchain-adoption.md`,
 2026-10-26.
Read that decision first;
 this file carries only the concrete shapes the implementation must produce.

## Command grammar

- `mise run toolchain:sync`:
 converge every tool to `toolchain.lock.json`.
 Alias target of `bootstrap` and `prepare:android`.
 Also runnable as `node package/dev-script/file-enforcer/src/toolchain/sync.ts`.
- `mise run toolchain:status`:
 print observed versus locked versions and exit non-zero on drift.
 Also runnable as `node package/dev-script/file-enforcer/src/toolchain/status.ts`.
- `mise run toolchain:update`:
 re-resolve the floating requests and channel stamps to their current
 upstream versions,
 rewrite `toolchain.lock.json`,
 regenerate the manifests,
 and print `id old -> new` per tool.
 `--check` reports and exits 1 when anything would move,
 writing nothing.
 Explicit pins never move without a plan edit.
 Also runnable as `node package/dev-script/file-enforcer/src/toolchain/update.ts`.
 Resolution sources per family
 (each probe-verified,
 maintainer policy 2026-10-26):
 npm-family tools follow the registry's `latest` dist-tag,
 so a publisher rollback can move a tool down in the update diff;
 `cargo:` follows crates.io's highest stable version,
 `mpm-uvx` follows PyPI,
 the GitHub families follow release tags and asset digests,
 node follows its SHASUMS256 files,
 `java` follows the Adoptium `temurin-21` stamp,
 `rust` follows the rustup nightly channel date,
 and `android-sdk` follows Google's cmdline-tools revision
 (its `androidPackages` pins stay fixed).
- `node package/dev-script/file-enforcer/src/toolchain/bin-paths.ts`:
 print the exposure directory,
 PATH directories,
 and one absolute path per linked binary as JSON
 (consumers such as the IDE read this instead of `mise bin-paths`).
 The output shape is exactly:

```jsonc
{
  "exposureDir": ".cache/toolchain-bin",
  "pathDirs": ["/abs/path/to/.cache/toolchain-bin", "/abs/path/.cargo/bin"],
  "bins": { "taplo": "/abs/path/.cache/toolchain-bin/taplo" }
}
```

## Paths

- Machine-level install root:
 `${XDG_DATA_HOME:-$HOME/.local/share}/monochromatic-dev/toolchain`
 (archives,
 Adoptium JDK,
 Android SDK),
 with `bin/` holding links to installed binaries.
- Manager-native installs stay manager-native
 (Cargo home for `cargo-binstall`,
 npm's global prefix,
 uv/pipx homes,
 rustup's own home),
 so `mpm`'s built-in managers can list them.
- Per-worktree exposure directory:
 `.cache/toolchain-bin` (gitignored),
 one symlink per tool binary,
 created atomically (temporary name plus rename,
 the `cli-git-bin` postinstall pattern).
 It is the first `_.path` entry in the generated mise `[env]`,
 replacing the `cli-git-bin` comment story.

## `toolchain.lock.json`

Generated by file-enforcer from the typed plan,
 committed,
 stable key order.
Top level:

```jsonc
{
  "schemaVersion": 1,
  "generatedFrom": "package/dev-script/file-enforcer/src/toolchain/plan.ts",
  "tools": {
    "node": {
      "request": { "track": "latest" },
      "version": "26.12.0",
      "route": "archive",
      "manager": null,
      "packageId": null,
      "bins": ["node", "npm", "npx"],
      "os": null,
      "env": {},
      "artifacts": {
        "linux-x64": {
          "url": "https://nodejs.org/dist/v26.12.0/node-v26.12.0-linux-x64.tar.gz",
          "sha256": "d9f88af7..."
        }
      }
    }
  }
}
```

- `request`:
 `{ "track": "latest" }` for the 53 floating entries,
 `{ "pinned": "1.3.14" }` for `bun`,
 `cargo:cargo-fuzz`,
 `zig`,
 `llama.cpp`,
 and `{ "channel": "nightly" }` / `{ "channel": "temurin-21" }` for `rust` and `java`.
- `route`:
 `bin-sourced`,
 `archive` (fallback for sources or payload shapes `bin` cannot fetch),
 `cargo-binstall`,
 `mpm-pnpm`,
 `mpm-uvx`,
 `rustup-toolchain`,
 `rustup-components`,
 `android-sdk`.
- `artifacts` carries the URL and SHA-256 `mise.lock` records today,
 keyed by the same platform ids.
 `mise.lock` currently has Linux targets only
 (`doc/decision/mise-lock-linux-only-stopgap.md`);
 preserve that honestly and leave macOS/Windows artifact rows absent.

## `mpm.packages.toml`

`mpm dump` format,
 generated from the plan,
 one section per MPM manager id,
 entries `package_id = "<version>"`.
Every managed tool appears here as the declared desired state;
 `toolchain:sync` restores only the managers whose adapters honor the recorded version
 (currently `rustup`),
 and marks the rest `route`-owned by providers until MPM forwards versions
 (`doc/troubleshooting/mpm-manager-extensibility.md`).

## `mpm.managers.toml`

Committed trusted local manager definitions
 (owner-writable only),
 used only where a definition expresses a pin that a shipped adapter drops.
Validate with `mpm --validate-config mpm.managers.toml`.

## Sync algorithm

1. Ensure `mpm` itself
 (pinned standalone release binary into the toolchain `bin/`,
 SHA-256 checked).
2. Ensure staging prerequisites:
 `cargo-binstall` first (other Cargo tools depend on it),
 Node before npm-backed entries,
 uv before uv/pipx entries.
3. `mpm restore` for the capable slice,
 with `--manager` selectors.
4. Provider installs for every remaining entry in plan order,
 idempotent (probe observed version first),
 each pinned to `toolchain.lock.json`.
5. Rust components and Android targets after the Rust toolchain;
 Android SDK components after cmdline-tools.
6. Postinstall steps
 (`cargo:monochromatic-git-policy-cli` atomic `git` link into `.cache/cli-git-bin`).
7. Rebuild `.cache/toolchain-bin`,
 verify every declared `bins` entry resolves,
 print the drift report.

## Routing (user-confirmed 2026-10-26)

The maintainer chose the installer per tool family:

- `bin-sourced`:
 every standalone tool whose artifact the `bin` CLI can fetch
 (GitHub releases,
 release-tag URLs,
 host sources such as `releases.hashicorp.com`),
 installed by `bin install <source spec>` at the repository boundary and
 inventoried and upgraded afterwards by MPM's `bin` manager
 (`https://mpm.run/managers/bin/`,
 whose own `install` operation is deliberately absent because listings report
 absolute paths,
 not source specs).
 Measured constraint (2026-10-26):
 `bin` installs exactly one file per invocation and re-downloads the asset on
 every call,
 so `bin-sourced` covers single-binary payloads
 (alias names such as `bunx` or `pnpm` link to the one inode),
 and the `archive` fallback covers multi-binary or whole-tree payloads
 (`age`,
 `cmake`,
 `llama.cpp`,
 `uv`,
 `taplo`,
 the JDK,
 Node,
 `zig`,
 `bubblewrap`) as well as sources `bin` cannot fetch.
- `cargo-binstall`:
 the `cargo:` tools.
- `mpm-pnpm` and `mpm-uvx`:
 the npm CLI tools through MPM's `pnpm` manager id,
 `pipx:slopo` through MPM's `uvx` manager id
 (the one wrapping `uv tool install`).
 Where an MPM adapter drops the version parameter,
 the sync runs the manager command with the locked version at the
 repository boundary and leaves inventory and upgrades to the MPM manager.
- `rustup`:
 the Rust toolchain through MPM's `rustup` manager (toolchain ids carry the exact channel),
 components and Android targets through direct `rustup component add` / `rustup target add`.
- `android-sdk`:
 the Android SDK,
 a repository provider running the Android CLI shipped in cmdline-tools
 (`android sdk install <package>[@<version>]...`,
 package ids such as `ndk/29.0.13846066` and `platform-tools`,
 listed by `android sdk list`),
 exporting `ANDROID_HOME` through the tool env file.

The maintainer's "no pinning" wording is recorded as:
 declarations keep floating requests and carry no `@version` pin syntax;
 `toolchain.lock.json` fixes what the sync installs,
 the same semantics `mise install` had against `mise.lock`,
 so the explicit pins (`bun` `1.3.14`,
 `zig` `0.15.2`,
 `llama.cpp` `b9829`,
 `cargo:cargo-fuzz` `0.13.2`) still install exactly.
 Sync semantics follow pnpm (maintainer 2026-10-26):
 `toolchain:sync` installs the locked versions the way `pnpm install`
 honors `pnpm-lock.yaml`,
 and re-resolving versions is a separate update action,
 the `pnpm update` analogue.

## Provider rules

- `bin-sourced`:
 `bin install <source spec> [name] -n '<glob>'`,
 after seeding the `bin` config `default_path`
 (resolution order `BIN_CONFIG`,
 `$HOME/.bin/config.json`,
 `$XDG_CONFIG_HOME/bin/config.json`,
 `$HOME/.config/bin/config.json`)
 so the first-run download-directory prompt never appears;
 alias names are links to the one installed inode.
- `archive`:
 download to a temp file in the toolchain root,
 verify SHA-256 before extraction,
 extract into `<root>/<id>/<version>/`,
 link `bins` into `<root>/bin` and `.cache/toolchain-bin`.
- `cargo-binstall`:
 `cargo binstall --no-confirm --version <locked> <crate>` plus `--features`
 when the plan records them,
 then the postinstall hook.
 The install runs at the repository boundary;
 any `mpm.managers.toml` entry for the family describes inventory only.
- `mpm-pnpm` / `mpm-uvx`:
 `pnpm add --global <name>@<locked>` and `uv tool install <name>==<locked>`
 at the repository boundary where the MPM adapter drops versions;
 inventory and upgrades stay with the MPM manager.
- `rustup-toolchain`:
 `rustup toolchain install <id>` where the id is the exact locked toolchain string;
 `rustup-components` runs `rustup component add` / `rustup target add` for the plan's lists
 (`doc/troubleshooting/mise-rust-components.md` explains why they only apply at install).
- `android-sdk`:
 install cmdline-tools from the locked archive,
 accept SDK licenses non-interactively,
 then `android sdk install <package>[@<version>]...` for the plan's pins
 (values currently in `prepare:android`:
 `platforms/android-37.0`,
 `build-tools/37.0.0`,
 `ndk/29.0.13846066`,
 `platform-tools`,
 with the exact ids confirmed through `android sdk list`).

## Tool environment exports

`ANDROID_HOME`,
 `ANDROID_SDK_ROOT`,
 `JAVA_HOME`,
 and `RUSTUP_TOOLCHAIN` move from tool plugins to a generated,
 gitignored env file at `.cache/toolchain.env.json`,
 loaded by a second `_.file` entry in the generated mise `[env]`
 (next to `.env.local.json`).
No machine-absolute path is committed.

## Cutover

The cutover is a hard switch that follows a successful full sync on the machine
 (maintainer correction 2026-10-26):
 a sync that cannot provision a tool is a hard error before any reader flips,
 and the Mise installs stay as the rollback until the maintainer prunes them.

1. Remove `[tools]`,
 `lockfile`,
 `lockfile_platforms`,
 `auto_install`,
 `disable_backends`,
 `status.missing_tools`,
 `minimum_release_age_excludes`,
 `[settings.pipx]`,
 `[settings.npm]`,
 `[settings.cargo]` from `mise.no-env.toml`,
 keeping tasks,
 templates,
 hooks,
 `[vars]`,
 and `env_shell_expand`.
2. Regenerate `mise.toml` with `node package/dev-script/file-enforcer/src/cli.ts`.
3. Delete `mise.lock`;
 retire `lock:mise`;
 repoint `bootstrap` to `toolchain:sync`.
4. Repoint every `mise.lock` reader to `toolchain.lock.json`:
 `.github/actions/task-cli-setup/action.yml`,
 `.github/workflows/music-player-release.yml` (the `awk` Rust scrapers),
 `.github/workflows/kotlin-linter-publish.yml`,
 `package/music-player/desktop-app/Containerfile.windows-gnu`.
5. Keep `mise trust` wording only where tasks still need trust.

## Consumers

- `package/desktop-app/ide/src/language/mise/*` becomes `language/toolchain/*`,
 querying `bin-paths.ts` output instead of `mise config ls --json` / `mise bin-paths`.
- `package/dev-script/vm-builder/Containerfile` and
 `package/config/dotfiles/mise/config.toml` stop seeding tool management.
- Root `Dockerfile`,
 `package/cli/mutation-test/runtime/Containerfile` install from `toolchain.lock.json` pins
 (or keep their own pins and cite the lock).

## Verification

1. `mise run toolchain:status` clean on this machine after a sync.
2. Disposable home (`mktemp -d`,
 `HOME=` and `XDG_DATA_HOME=` overrides,
 container with 2 GiB / 2 CPUs):
 sync the Linux x64 slice,
 then run one TypeScript task,
 one Rust task and one lint task through `mise run`.
3. `mpm installed` and `mpm outdated` list the manager-backed tools.
4. No synthetic host load
 (the synthetic-load ban),
 and every probe reports the command,
 working directory and exit status.

## Known limits to record, not paper over

- macOS and Windows provisioning parity is unverified here
 (the tool acquisition parity gate stays open).
- Floating requests keep today's semantics
 (intent floats,
 resolution is locked);
 the floating-versus-exact preference stays open in
 `doc/planning/mise-removal-coverage.md`.
- `mise.lock`'s Linux-only artifact rows are carried over as-is;
 resolving the other platforms is follow-up work.

## Implementation record (toolchain-core, 2026-10-26)

Shape additions and clarifications the implementation needed;
 the shapes above stand otherwise.

- `toolchain.lock.json` tool records carry an `options` key after `env`
 (the decision doc's "provider options":
 rust components and targets,
 cargo features,
 Android SDK package pins,
 the postinstall link,
 bin aliases,
 and bootstrap metadata).
- `env` values are toolchain-root relative paths (`java/<version>`)
 or literal strings (`RUSTUP_TOOLCHAIN`),
 never machine-absolute;
 `toolchain:sync` resolves them when writing `.cache/toolchain.env.json`.
- The plan declares two bootstrap entries besides the 59 tools:
 `bin`
 (standalone release binary,
 SHA-256 checked against the release `checksums.txt` values)
 and `mpm`.
 `mpm`'s distribution is the PyPI wheel `meta-package-manager` 8.2.0,
 SHA-256 checked against PyPI's published digest
 and installed with `uv tool install`.
 Corrected 2026-10-26:
 an earlier draft of this record said the GitHub release assets returned
 404;
 those probes addressed a misspelled repository
 (`kdeldyde` instead of `kdeldycke`),
 and `gh repo view kdeldycke/meta-package-manager` reports the repository
 public.
 The wheel route stands as implemented because it is verified and matches
 mpm.run's own PyPI-first install guidance,
 not because GitHub is absent.
 `uv` is staged before `mpm` for that reason.
- Staging order is `bin`,
 `uv`,
 `mpm`,
 `rust`,
 `cargo-binstall`,
 `node`,
 `pnpm`,
 then the remaining tools in plan order
 (the staging list above extended with the bootstrap prerequisites).
- `mpm restore` is invoked with mpm's global manager selectors
 (`mpm --rustup restore mpm.packages.toml`),
 not a `--manager` flag.
- `mpm.packages.toml` sections are `[cargo]`,
 `[conda]`,
 `[pnpm]`,
 `[rustup]` and `[uvx]`
 (the `uvx` manager wraps `uv tool install`;
 the `uv` id wraps `uv pip` and exposes no CLI).
 `bin-sourced` tools are not declared there:
 mpm's `bin` manager inventories absolute paths,
 which cannot be committed portably.
- `mpm.managers.toml` definitions cover the `cargo:` tools only:
 their pins ride in a `--version` argument
 (no `@version` syntax in declarations),
 while the `pnpm` adapter's only pin channel is `@version` package syntax,
 so npm tools stay provider-owned at the repository boundary.
- `taplo`'s `mise.lock` row recorded a blake3 digest for `linux-x64`;
 `toolchain.lock.json` records the SHA-256 of the same artifact bytes,
 computed 2026-10-26,
 so every artifact row is a checkable SHA-256.
- Provider boundary commands derive their pins from the lock:
 `cargo binstall --no-confirm --version <locked> <crate>`,
 `pnpm add --global <name>@<locked>`,
 `uv tool install <name>==<locked>`,
 `bin install <release-tag-url> -n '<asset>/**/<bin>'`,
 and `android sdk install <package>...`.
- `bin-paths.ts` prints `exposureDir` as the literal `.cache/toolchain-bin`
 and `pathDirs` with its absolute realization first,
 then the manager-native bin directories that exist;
 unprovisioned toolchains print empty `pathDirs` and `bins` and exit 0.
 Entry-point guards compare real paths,
 so symlinked home directories still dispatch.
