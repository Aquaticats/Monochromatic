## Budget incompatibility and routes without new access

An unconditional all-provider invoice guarantee is not established by a repository ledger.
The ledger cannot observe unrelated usage,
opening commitments,
or all persistent storage charges.
Public minute admission caps do not close that gap.
The existing USD 200 ceiling remains unchanged;
calling a partial estimate a hard cap would misstate its enforcement.

A workable division of responsibility is an owner-reserved allocation inside that ceiling.
The owner accounts for commitments outside the program;
the implementation admits only bounded work against the allocation it is given.
Both the opening allocation and its external commitments remain owner assertions,
not independently verified invoices.
Account-wide inspection is not required for this arrangement.
The authorization needs an explicit validity period;
missing or expired headroom fails closed.
Where remaining included allowances cannot be inspected,
reserve full published charges for the selected resource class
rather than assuming unused credits or a universal price per normalized minute.

An alternative is owner authorization of each paid batch.
Without an applicable allocation or batch authorization,
new billable work remains paused and eligible GitHub work can continue.
This fallback does not erase already committed charges.
Resources whose worst-case exposure cannot be bounded remain outside automatic admission
until their retention or charge boundary is established.
Mutable storage and overlapping allocations cannot silently be treated as free.

## Settled-prerequisite frontier draft

These independent decisions can now be presented together after the completed cache-result reconciliation.
The wording is planning material,
not user-facing questions already sent.

### Spend authority under the existing ceiling

- Standing owner-reserved allocation:
  authorize bounded autonomous CI against a monthly allocation inside USD 200,
  with admission paused when the allocation is missing,
  expired,
  or insufficient for the exposure bound.
  This supports agent-requested execution with fewer interruptions;
  the owner retains responsibility for unobserved commitments and the allocation itself.
- Explicit paid-batch authorization:
  authorize each paid batch against owner-held remaining headroom.
  This gives direct control over commitments;
  it adds interruptions and may delay useful feedback.

Recommendation and ranking:
standing allocation > explicit paid batches,
because autonomous requested checks are already a desired capability
and the standing allocation can retain conservative admission bounds.
Neither choice authorizes new account access,
changes the USD 200 ceiling,
or proves an aggregate invoice independently.

### Enforcement of qualified new validation

- Enforce qualified checks at agreed release or promotion boundaries:
  regressions can stop publication after the lane's acceptance controls pass.
  This gives expanded coverage an enforceable effect;
  a failure can delay the corresponding release or promotion.
- Keep new checks advisory:
  publish complete results and failures while existing enforcement stays unchanged.
  This avoids new release interruptions;
  passing publication can coexist with a reported validation failure.

Recommendation and ranking:
qualified enforcement > advisory-only,
because the requested expansion includes behavioral and packaged-consumer correctness.
An observation phase precedes qualification in either design.
This does not propose changing direct-commit or auto-push habits.
Exact required checks and any repository-protection changes follow the selected enforcement policy.

### Autonomy for infrastructure retry and fallback

- Automatic bounded recovery:
  permit a limited retry or eligible alternate-provider attempt for classified infrastructure failures,
  within the existing reservation and with the original failure preserved.
  This can restore useful feedback without intervention;
  it can add work and requires conservative classification and reservation rules.
- Explicit recovery request:
  report the infrastructure failure and require an authorized rerun request.
  This avoids automatic duplicate attempts;
  it adds interruption and recovery latency.

Recommendation and ranking:
automatic bounded recovery > explicit recovery request,
because resilience supports the desired cloud workflow
while actual source failures remain failures.
Queue thresholds and retry counts are engineering parameters to recommend from measured profiles,
not extra preference questions.
