Generated 2026-05-28 from a critical review of
[`package/ssg/aquati.cat/TODO.generalize-ssg.md`](../../package/ssg/aquati.cat/TODO.generalize-ssg.md),
the plan to extract `ssg-test` into a publishable,
 general-purpose static site generator
(`@monochromatic-dev/ssg`) with the Aquaticat content split into a new `site-aquaticat` package.

Verdict:
 the plan is not salvageable by patching.
It was created 2026-04-06 and last touched 2026-05-17 (a trivial ticker-quote fix),
and it describes a codebase that no longer matches reality.
The recommendation is to discard its i18n portions and rebuild on the already-decided
Phase 6 migration in [`doc/planning/module-i18n-compose.md`](../planning/module-i18n-compose.md),
then re-derive the genericization work against the real publishability and path-model constraints.

## Headline: the plan predates the decided i18n architecture and was never reconciled

`TODO.generalize-ssg.md` rebuilds i18n around `typesafe-i18n`.
A fully-implemented replacement,
 `@monochromatic-dev/module-i18n-compose`,
 landed 2026-05-18
(type-checks,
 lints clean,
 all tests pass),
 and `doc/planning/module-i18n-compose.md`
carries a Phase 6 migration plan written for this exact package.
The generalize plan's headline feature,
 user-configurable arbitrary languages,
 is a documented
non-goal of the chosen architecture (`doc/planning/module-i18n-compose.md:1104`:
"no support for arbitrary languages until a real consumer needs them").

This reframes the verdict from "a plan with bugs" to "a plan written without knowledge of the
committed architecture.
" The i18n cluster below (defects 1 to 5) are facets of that one root failure.

## Defects (20)

These are verified against the source,
 cited by repo-relative path and line.

1. Phase 2 plumbs config into `typesafe-i18n`,
    which is being deleted.
   The migration to `module-i18n-compose` is decided and built;
    Phase 6 (the `ssg-test` migration)
   is the pending step.
    The plan's entire i18n section rests on a removed foundation.

2. "Configurable languages" contradicts a closed-set architecture.
   The config schema advertises `languages` as a record of arbitrary language codes.
   The chosen design ships hand-written grammar builders for exactly `ca`,
    `en`,
    and `zh`
   (`defineEnglishLocale`,
    `defineChineseLocale`,
    `defineCatalanLocale`;
   `doc/planning/module-i18n-compose.md:322-328`).
   Adding a language means writing a new grammar renderer module,
    not editing config.

3. `config.languages[lang].i18n` as a runtime override map is incompatible with the new model.
   UI strings are a compile-time `Label` union rendered via `i18n.label(locale, key)`
   (`doc/planning/module-i18n-compose.md` sections 6 and 3),
    not a runtime partial-record override.

4. siteName and siteDescription mechanism conflict.
   The plan moves them into config and deep-merges them into `typesafe-i18n` translation objects;
   the decided architecture treats them as consumer-owned `label` entries
   (`doc/planning/module-i18n-compose.md:142,211`).

5. "Update `i18n-types.ts`" edits a generated file.
   Its header reads "auto-generated by typesafe-i18n.
    Any manual changes will be overwritten,
   "
   and the file is on the deletion list anyway (`doc/planning/module-i18n-compose.md:1019-1024`).

6. "Create a Zod schema" (Phase 1,
    stated twice) names the wrong library.
   The repo standardized on valibot (`src/lib/content.ts:21,162`;
    the `config-schemas.ts` convention
   in `package/pi-plugin/advisor`,
    `package/pi-plugin/auto-mode`,
    `package/webapp-productivity/rss`;
   `doc/migration/zod-to-valibot.md`).
    zod is not a dependency.
   `src/lib/content.ts:5` even carries a stale "validates with Zod" comment over valibot code;
   the plan inherited that stale mental model.

7. Catalan is dropped.
   `ca` is a full locale:
    `src/i18n/ca/index.ts`,
    16 files under `src/content/ca/`,
   `LANG_NAMES.ca = 'Català'`.
    The i18n step names only `en` and `zh`,
    the config example has only
   `en` and `zh`,
    and Phase 3's content-move list omits `content/ca`.

8. Phase 2's per-file task list misreads the i18n coupling.
   It says `pages/index.ts` just needs "config passed to templates.
   "
   It actually imports `i18nObject` and `locales` from the generated `i18n-util.ts` (the file being deleted).
   Eleven non-generated source files import the generated i18n:
    `src/build.ts`,
   `src/components/lang-switcher.ts`,
    `src/components/site-header.ts`,
    `src/lib/content.ts`,
   `src/lib/rss.ts`,
    `src/pages/{index,lang,name,post,tag}.ts`,
    `src/templates/head.ts`.
   The plan never redirects them.

9. `PIPELINE_GLOB` is misclassified as a safe-to-leave default.
   The plan lists "Pipeline source paths for cache invalidation" under "stays as SSG default (not configurable).
   "
   But `PIPELINE_GLOB = 'src/{lib,components,client}/**/*.ts'` (`src/build.ts:73`) is cwd-relative to the
   SSG's own source.
    When the SSG is a `node_modules` dependency it matches nothing in the consumer's cwd,
   so the cache never invalidates on an SSG change.

10. The same glob is broken for a second,
     independent reason.
    It omits `src/i18n/`;
     the i18n migration requires widening it so i18n changes invalidate rendered output
    (`doc/planning/module-i18n-compose.md:139`,
     acceptance at `:1089`).
    The plan's "leave it as a default" is wrong twice over.

11. Phase 5 ("publishable to npm") ignores private dependencies.
    The SSG depends on `module-logger` (`private: true`) and `module-fs-path` (`private: true`).
    Publishing requires un-privating and publishing them,
     or bundling.
     The plan never mentions it.

12. Bundling does not fix the runtime coupling in `module-fs-path`.
    `src/lib/git-dates.ts:97,262` call `findMiseMonorepoRootCached()`,
     which assumes a mise monorepo root.
    A third-party consumer is not in one,
     so the date pipeline breaks regardless of how the dependency is packaged.

13. `git-dates.ts` assumes this exact environment and is never mentioned by the plan.
    It uses `git log --follow`,
     `getGithubSlug()` parsing `owner/repo` from the `origin` remote,
    and the GitHub REST API via `gh` for shallow clones.
    None of that holds for an arbitrary npm consumer.

14. The rename creates an unflagged name-to-path mismatch.
    Package names encode the directory path (`package/git-policy/cli` to `cli-git`,
    `package/module/i18n-compose` to `module-i18n-compose`).
    Phase 4 renames to `@monochromatic-dev/ssg` while keeping the package at `package/webapp-content/ssg/`,
    where the convention yields `@monochromatic-dev/webapp-content-ssg`.
    The plan never acknowledges the inconsistency or resolves which of the name or the path should change.

15. There is no invocation model.
    The build entry is `node src/build.ts` (`mise.toml`),
     and `package.json` has no `bin`.
    Phase 3 says site-aquaticat gets "`mise.toml` with build/dev tasks that invoke the SSG" but never specifies
    how a consumer triggers a build whose entry lives in `node_modules`,
     nor how the `extends` task templates
    (`build:js:client`,
     `lint`,
     defined in the root `mise.toml:172,391`) resolve for a package outside this monorepo.

16. The rename surface is understated.
    Phase 4 says "update `pnpm-workspace.yaml` if the path is listed explicitly.
    "
    There is a live functional reference at `mise.toml:619`
    (`package/ssg/aquati.cat/node_modules/.bin` in a PATH list),
    plus rationale comments in `pnpm-workspace.yaml:243,309,313`.
    The vague phrasing invites missing the functional one.

17. Brand identity is provably non-configurable in part.
    `src/templates/head.ts:151-163` hardcodes `#bf97e3` and `#4e318f` as `theme-color` meta tags.
    Those are not CSS custom properties,
     so the plan's claim that "design tokens are overridden via CSS
    custom properties,
     not config" is incomplete on its face.
    Supporting evidence:
     `src/styles/tokens.ts:120-121` defines the same colors as `--primary-light` and
    `--primary-dark`,
     the styles compile to a single `styles.css`,
     and no consumer CSS injection point exists
    in `src/build/assets.ts` (scope of the search:
     `assets.ts`,
     not every styles path).

18. Co-located content images are not in the move list.
    `src/content/*.{avif,jpg,png}` sit beside,
     not under,
     the locale directories.
    Phase 3 moves `content/en/*.mdx` and `content/zh/*.mdx` but is vague about these images
    and omits `content/ca` entirely.

19. The license split is unaddressed.
    The package is `LGPL-3.0-or-later AND CC-BY-SA-4.0`;
     the CC-BY-SA covers Aquaticat content.
    After the content moves to site-aquaticat,
     the SSG carries LGPL-3.0-or-later only and
    site-aquaticat carries CC-BY-SA-4.0.
     Phase 5's "ensure correct license" never notes the split.

20. The self-assessment is inverted.
    "Low risk,
     no architectural changes,
     just plumbing a config object,
     roughly 1.5 days" is contradicted by
    defects 1 to 16:
     the i18n replacement,
     the cwd-versus-package-root path model,
     and publishability are all
    architectural.
     The estimate rests on a survey the plan never performed,
     and the plan has not been touched
    substantively since before the architecture it ignores was built.

## Design questions the plan left unresolved (5)

These are judgment calls,
 not defects,
 but the plan resolves them silently or not at all.

- Caddyfile placement.
   Phase 3 calls it "site-specific dev server config.
  "
  It is mostly generic SSG-output serving (try_files,
   hashed-asset cache headers,
   port 4321).
  A site wanting its own port or TLS is a real reason to move it,
   but the boilerplate arguably belongs with the
  SSG as a default.
   The plan does not weigh this.
- Category placement.
   A general-purpose,
   publishable build tool living under `package/webapp-content/`
  (the content and site category,
   beside site-aquaticat) is arguably miscategorized;
  build tools live under `cli/` or `module/`.
   Overlaps defect 14.
- Fixed frontmatter schema.
   `src/lib/content.ts:158-166` hardcodes `{ title, description, tags }`.
  Many SSGs ship a fixed core schema,
   so this is defensible,
   but a "general-purpose" SSG with no schema
  extension is a limitation the plan never raises.
- Build tool dependencies.
   `pagefind` (search) and `caddy` (dev) are mise tools the pipeline needs.
  Phase 5 and the proposed site-aquaticat `mise.toml` do not account for a consumer needing them.
- Fonts.
   `fonts-source/*.woff2`,
   `public/*.woff2`,
   and `src/build/subset-fonts.ts`
  (subsets by glyph usage in `src/`) are never classified as SSG-default or site-asset,
  yet Phase 3 moves `public/`.

## Recommendation

Discard the i18n portions of the plan and build on the Phase 6 migration in
`doc/planning/module-i18n-compose.md`.
Re-derive the genericization work against the real constraints surfaced above:
 the closed locale set,
the cwd-versus-package-root path model,
 the private-dependency and environment-coupling publish blockers,
and the naming and invocation model.
 The genuinely simple parts of the original plan
(threading `url`,
 `contentDir`,
 `favicon.source`,
 `favicon.backgroundColor`,
 and `tickerQuotes` through the
pipeline) remain valid and can be carried forward.
