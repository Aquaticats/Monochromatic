## Scope

This report explains each entry in the supplied published `turso` crate manifest for version `0.6.1`:
package metadata generated by Cargo,
 features,
 runtime dependencies,
 development dependencies,
Cargo targets,
 lint configuration,
 dependency feature flags,
 and dependency default-feature settings.

Data quality note:
 evidence is primary source unless marked otherwise.
I used the published `docs.rs` crate source,
 the upstream `v0.6.1` Git tag,
and Cargo or Rust documentation for manifest semantics.
The `docs.rs` manifest says it is Cargo-normalized and points to `Cargo.toml.orig` for the original manifest:
<https://docs.rs/crate/turso/0.6.1/source/Cargo.toml>
The original `turso` member manifest is shorter and inherits workspace values:
<https://docs.rs/crate/turso/0.6.1/source/Cargo.toml.orig>
The published crate's `.cargo_vcs_info.json` maps the crate package to upstream path `bindings/rust`
and commit `76af5a1250cd98bb26c13862093a638714b0a3a6`:
<https://docs.rs/crate/turso/0.6.1/source/.cargo_vcs_info.json>
The upstream tag audited locally resolves to the same commit.
I treat `bindings/rust/rust-driver-sync.mdx` only as a checked-in implementation note,
because its contents are prompt-like;
 source code and manifests are the primary evidence for dependency rationale.

## Executive findings

- Most visible verbosity comes from Cargo registry normalization,
   not hand-written Turso configuration.
  The published file expands workspace inheritance,
   path dependencies,
   auto-discovered targets,
  and inherited lints into a standalone crate manifest:
  <https://docs.rs/crate/turso/0.6.1/source/Cargo.toml>
- The core Rust API wraps `turso_sdk_kit` for database,
   connection,
   statement,
   value,
   and error APIs,
  and re-exports `turso_core` for lower-level engine access:
  <https://github.com/tursodatabase/turso/blob/v0.6.1/bindings/rust/src/lib.rs#L49-L65>
- The default feature set opts users into `mimalloc` and FTS.
  `mimalloc` installs a global allocator on non-Wasm and non-Miri targets,
  while FTS forwards to `turso_sdk_kit/fts` and then `turso_core/fts`,
   which enables Tantivy-backed search:
  <https://docs.rs/crate/turso/0.6.1/source/Cargo.toml.orig>
  <https://github.com/tursodatabase/turso/blob/v0.6.1/bindings/rust/src/lib.rs#L35-L37>
  <https://github.com/tursodatabase/turso/blob/v0.6.1/sdk-kit/Cargo.toml#L10-L14>
  <https://github.com/tursodatabase/turso/blob/v0.6.1/core/Cargo.toml#L41-L68>
- The `sync` feature gates the Rust `sync` module and the HTTP/Tokio dependency stack,
  but `turso_sync_sdk_kit` itself is a normal dependency in the original manifest rather than an optional dependency:
  <https://docs.rs/crate/turso/0.6.1/source/Cargo.toml.orig>
  <https://github.com/tursodatabase/turso/blob/v0.6.1/bindings/rust/src/lib.rs#L45-L46>
- Local `cargo tree` against `/tmp/agent/turso-v0.6.1-20260620/Cargo.toml`,
   with package `turso`,
  no default features,
   and depth 1,
  verified that `turso_sync_sdk_kit`,
   `tracing`,
   and `tracing-subscriber` remain direct dependencies with default
  features disabled.
   Local `cargo tree` with `--no-default-features --features sync --depth 1` verified that
  `bytes`,
   `http-body-util`,
   `hyper`,
   `hyper-tls`,
   `hyper-util`,
   and runtime `tokio` appear with `sync` enabled.
- Three entries look overdeclared from the Rust binding source alone:
  `tracing` has no direct `bindings/rust` source reference found by local `rg`,
  `tracing-subscriber` is used only in test modules,
  and `rand_chacha` has no direct `bindings/rust` source reference found by local `rg`.
  The manifest still may keep them for workspace consistency or unreleased work,
  but the audited source does not show runtime use in the `turso` binding crate:
  <https://docs.rs/crate/turso/0.6.1/source/Cargo.toml.orig>

## Why the published manifest is so long

### Registry normalization

Cargo rewrites manifests uploaded to the registry for compatibility and rewrites path dependencies into registry
version dependencies.
 The published file states this directly in its generated header:
<https://docs.rs/crate/turso/0.6.1/source/Cargo.toml>

The original `bindings/rust/Cargo.toml` uses workspace inheritance for `version`,
 `authors`,
 `edition`,
 `license`,
`repository`,
 dependencies,
 and lint configuration:
<https://docs.rs/crate/turso/0.6.1/source/Cargo.toml.orig>
The workspace provides those inherited values and path dependencies:
<https://github.com/tursodatabase/turso/blob/v0.6.1/Cargo.toml#L89-L129>

### Package identity and registry metadata

`name = "turso"` is the crate name dependents put in their `Cargo.toml`.
Cargo documents `name` as the package identifier used when listed as a dependency:
<https://doc.rust-lang.org/cargo/reference/manifest.html#the-name-field>

`version = "0.6.1"`,
 `authors = ["the Turso authors"]`,
 `edition = "2021"`,
 `license = "MIT"`,
and `repository = "https://github.com/tursodatabase/turso"` come from `[workspace.package]` in the upstream workspace:
<https://github.com/tursodatabase/turso/blob/v0.6.1/Cargo.toml#L89-L94>
Cargo documents `version`,
 `authors`,
 `edition`,
 `license`,
 and `repository` as package metadata fields:
<https://doc.rust-lang.org/cargo/reference/manifest.html#the-package-section>

`description = "Turso Rust API"` is local to the original binding manifest and is required for crates.
io publishing:
<https://docs.rs/crate/turso/0.6.1/source/Cargo.toml.orig>
<https://doc.rust-lang.org/cargo/reference/manifest.html#the-description-field>

`readme = "README.md"` is added by normalization because the package contains `README.md`.
Cargo documents `readme` as the package-root file transferred to the registry and rendered by crates.
io:
<https://doc.rust-lang.org/cargo/reference/manifest.html#the-readme-field>

### `build = false` and the `auto* = false` entries

`build = false` in the normalized manifest disables automatic build script detection.
Cargo documents `build = false` as the way to disable automatic detection of `build.rs`:
<https://doc.rust-lang.org/cargo/reference/manifest.html#the-build-field>

`autolib = false`,
 `autobins = false`,
 `autoexamples = false`,
 `autotests = false`,
 and `autobenches = false`
are published alongside explicit target sections in the normalized manifest.
Cargo documents these fields as controls for disabling automatic discovery of library,
 binary,
 example,
test,
 and benchmark targets:
<https://doc.rust-lang.org/cargo/reference/cargo-targets.html#target-auto-discovery>

### Explicit target sections

The normalized manifest lists `[lib]`,
 four examples,
 and two integration tests.
Cargo documents that examples under `examples/` and tests under `tests/` are target types that can be inferred
or written explicitly in the manifest:
<https://doc.rust-lang.org/cargo/reference/cargo-targets.html>

The original manifest explicitly lists only `sync_example`,
 because it requires the `sync` feature,
and `concurrent_writes`;
 the normalized manifest also lists auto-discovered `example`,
 `example_struct`,
`integration_tests`,
 and `test_deadlock_join`:
<https://docs.rs/crate/turso/0.6.1/source/Cargo.toml.orig>
<https://docs.rs/crate/turso/0.6.1/source/Cargo.toml>

## Feature entries

### `default = ["mimalloc", "fts"]`

Turso enables `mimalloc` and FTS by default in the original manifest:
<https://docs.rs/crate/turso/0.6.1/source/Cargo.toml.orig>
Cargo documents that default features are enabled unless callers opt out with `--no-default-features`
or `default-features = false`:
<https://doc.rust-lang.org/cargo/reference/features.html#the-default-feature>

### `mimalloc = ["dep:mimalloc"]`

This feature exists to opt the `mimalloc` optional dependency into the build.
The crate installs `mimalloc::MiMalloc` as the global allocator when the `mimalloc` feature is active,
the target is not Wasm,
 and the build is not Miri:
<https://github.com/tursodatabase/turso/blob/v0.6.1/bindings/rust/src/lib.rs#L35-L37>
Cargo documents `dep:` as syntax for grouping optional dependencies behind named features:
<https://doc.rust-lang.org/cargo/reference/features.html#optional-dependencies>
The workspace sets `mimalloc = { version = "0.1.47", default-features = false }`.
The audited source has no inline comment explaining that default-feature choice,
 so the report can only tie it to
Turso's direct allocator use rather than a stated upstream rationale:
<https://github.com/tursodatabase/turso/blob/v0.6.1/Cargo.toml#L115>

### `fts = ["turso_sdk_kit/fts"]`

This feature forwards FTS enablement to `turso_sdk_kit`,
 which forwards it to `turso_core/fts`:
<https://github.com/tursodatabase/turso/blob/v0.6.1/sdk-kit/Cargo.toml#L10-L14>
`turso_core/fts` enables the optional Tantivy dependency:
<https://github.com/tursodatabase/turso/blob/v0.6.1/core/Cargo.toml#L41-L68>
The FTS implementation imports Tantivy,
 defines the `fts` index method name,
and exposes helpers such as `fts_highlight`:
<https://github.com/tursodatabase/turso/blob/v0.6.1/core/index_method/fts.rs#L26-L83>
The SQL translator rejects `MATCH` when FTS is not enabled,
 which explains why the feature gate matters:
<https://github.com/tursodatabase/turso/blob/v0.6.1/core/translate/expr/functions.rs#L55-L91>

### `pure-rust-crypto`

The `turso` feature forwards to both `turso_sdk_kit/pure-rust-crypto` and
`turso_sync_sdk_kit/pure-rust-crypto`:
<https://docs.rs/crate/turso/0.6.1/source/Cargo.toml.orig>
`core` maps `pure-rust-crypto` to `aegis/pure-rust`.
The same `core` manifest comment says Android and macOS use pure Rust by default to avoid C cross-compilation issues,
and other targets can opt in through this feature:
<https://github.com/tursodatabase/turso/blob/v0.6.1/core/Cargo.toml#L35-L140>
The Rust binding re-exports `EncryptionOpts` from `turso_sdk_kit`,
 so crypto feature selection affects the exposed
local encryption API:
<https://github.com/tursodatabase/turso/blob/v0.6.1/bindings/rust/src/lib.rs#L137>
<https://github.com/tursodatabase/turso/blob/v0.6.1/sdk-kit/src/rsapi.rs#L36-L130>

### `stacker = ["turso_core/stacker"]`

This feature forwards stack instrumentation to `turso_core`.
The core feature enables the optional `stacker` dependency:
<https://github.com/tursodatabase/turso/blob/v0.6.1/core/Cargo.toml#L44-L119>
The stack module uses `stacker::remaining_stack()` under `#[cfg(feature = "stacker")]`
and logs stack samples when `TURSO_TRACE_STACK` is set:
<https://github.com/tursodatabase/turso/blob/v0.6.1/core/stack.rs#L14-L88>

### `sync`

The `sync` feature enables the HTTP and Tokio dependency stack:
 `hyper`,
 `tokio`,
 `hyper-tls`,
 `hyper-util`,
`http-body-util`,
 and `bytes`:
<https://docs.rs/crate/turso/0.6.1/source/Cargo.toml.orig>
The public `sync` module is compiled only with `#[cfg(feature = "sync")]`:
<https://github.com/tursodatabase/turso/blob/v0.6.1/bindings/rust/src/lib.rs#L45-L46>
The sync implementation builds `TursoDatabaseSync<Bytes>`,
 drives async operations,
 starts a Tokio IO worker thread,
streams HTTP response frames,
 and handles file read or write IO requests:
<https://github.com/tursodatabase/turso/blob/v0.6.1/bindings/rust/src/sync.rs#L281-L285>
<https://github.com/tursodatabase/turso/blob/v0.6.1/bindings/rust/src/sync.rs#L497-L564>
<https://github.com/tursodatabase/turso/blob/v0.6.1/bindings/rust/src/sync.rs#L636-L733>
<https://github.com/tursodatabase/turso/blob/v0.6.1/bindings/rust/src/sync.rs#L752-L783>

## Runtime dependencies

### `turso_core`

`turso_core` is the embedded database engine crate.
The Rust binding re-exports it as `turso::core` and accepts custom `Arc<dyn turso_core::IO>`
through `Builder::with_io_impl`:
<https://github.com/tursodatabase/turso/blob/v0.6.1/bindings/rust/src/lib.rs#L64-L65>
<https://github.com/tursodatabase/turso/blob/v0.6.1/bindings/rust/src/lib.rs#L153-L242>
The `stacker` feature also forwards to `turso_core`,
 which confirms the binding uses this crate for engine-level
feature selection:
<https://docs.rs/crate/turso/0.6.1/source/Cargo.toml.orig>

### `turso_sdk_kit`

`turso_sdk_kit` is the Rust binding's primary SDK layer.
`Builder::build` constructs `turso_sdk_kit::rsapi::TursoDatabase` with `TursoDatabaseConfig`,
sets `async_io: true`,
 and waits on delegated IO via the SDK kit:
<https://github.com/tursodatabase/turso/blob/v0.6.1/bindings/rust/src/lib.rs#L287-L302>
The binding maps `turso_sdk_kit::rsapi::TursoError` into its public `Error` enum:
<https://github.com/tursodatabase/turso/blob/v0.6.1/bindings/rust/src/lib.rs#L116-L130>
The `Connection`,
 `Rows`,
 and `Value` types wrap or convert `turso_sdk_kit::rsapi` connection and value types:
<https://github.com/tursodatabase/turso/blob/v0.6.1/bindings/rust/src/connection.rs#L44-L180>
<https://github.com/tursodatabase/turso/blob/v0.6.1/bindings/rust/src/rows.rs#L72-L101>
<https://github.com/tursodatabase/turso/blob/v0.6.1/bindings/rust/src/value.rs#L113-L136>

### `turso_sync_sdk_kit`

`turso_sync_sdk_kit` supplies the sync database config,
 sync operation API,
 partial sync types,
 stats type,
and sync IO queue integration:
<https://github.com/tursodatabase/turso/blob/v0.6.1/sync/sdk-kit/src/rsapi.rs#L16-L43>
The Rust binding's `sync` module re-exports sync stats and partial sync types from that crate:
<https://github.com/tursodatabase/turso/blob/v0.6.1/bindings/rust/src/sync.rs#L23-L25>
The same module constructs `TursoDatabaseSync<Bytes>` and calls sync operations such as `push_changes`,
`wait_changes`,
 `checkpoint`,
 `stats`,
 and `connect`:
<https://github.com/tursodatabase/turso/blob/v0.6.1/bindings/rust/src/sync.rs#L281-L407>

Audit note:
 unlike the HTTP/Tokio sync dependencies,
 `turso_sync_sdk_kit` is not optional in the original
manifest.
 If the intent is to keep non-sync builds lean,
 this is the dependency most worth rechecking:
<https://docs.rs/crate/turso/0.6.1/source/Cargo.toml.orig>

### `thiserror`

`thiserror` derives the public error implementation.
The binding declares `#[derive(Debug, thiserror::Error)]` for its `Error` enum:
<https://github.com/tursodatabase/turso/blob/v0.6.1/bindings/rust/src/lib.rs#L84-L113>

### `mimalloc`

`mimalloc` is optional and is activated by the default `mimalloc` feature.
The only audited binding use is the global allocator installation:
<https://github.com/tursodatabase/turso/blob/v0.6.1/bindings/rust/src/lib.rs#L35-L37>

### `hyper`

`hyper` supplies HTTP request construction,

<https://github.com/tursodatabase/turso/blob/v0.6.1/bindings/rust/src/sync.rs#L12-L14>

## Lint configuration

### Why `[lints]` appears in the normalized manifest

The original member manifest uses `[lints] workspace = true`:
<https://docs.rs/crate/turso/0.6.1/source/Cargo.toml.orig>
The workspace defines rustc and Clippy lint policy:
<https://github.com/tursodatabase/turso/blob/v0.6.1/Cargo.toml#L205-L217>
Rust 1.74 added Cargo manifest lint configuration and workspace lint inheritance:
<https://blog.rust-lang.org/2023/11/16/Rust-1.74.0/#lint-configuration-through-cargo>

### `unexpected_cfgs` with `loom`, `shuttle`, and `antithesis`

The workspace declares custom cfg names `loom`,
 `shuttle`,
 and `antithesis` as expected:
<https://github.com/tursodatabase/turso/blob/v0.6.1/Cargo.toml#L205-L206>
The normalized manifest includes `priority = 0`,
 which is Cargo's default lint priority for that entry:
<https://docs.rs/crate/turso/0.6.1/source/Cargo.toml>
Cargo documents lint `priority` as the integer that controls which lint settings override other lint settings:
<https://doc.rust-lang.org/cargo/reference/manifest.html#the-lints-section>
The core manifest has target dependencies keyed by those cfg names.
That explains why the project wants them recognized:
<https://github.com/tursodatabase/turso/blob/v0.6.1/core/Cargo.toml#L124-L132>
Cargo and rustc use `unexpected_cfgs` to warn on unknown cfg names and values,
and the Rust blog documents `check-cfg` entries for statically known custom cfg names:
<https://blog.rust-lang.org/2024/05/06/check-cfg/#expecting-custom-cfgs>

### Clippy denies

These lints are inherited from the workspace and are set to `deny`,
 so violations fail local linting for the crate:
<https://github.com/tursodatabase/turso/blob/v0.6.1/Cargo.toml#L208-L217>

- `or_fun_call`:
   prevents eager fallback construction in `Option::or` or `Result::or` patterns
  when lazy forms are intended.
  Clippy source:
   <https://rust-lang.github.io/rust-clippy/master/index.html#or_fun_call>
- `clear_with_drain`:
   catches `drain(..)` patterns that discard all items when `clear()` expresses the intent.
  Clippy source:
   <https://rust-lang.github.io/rust-clippy/master/index.html#clear_with_drain>
- `collection_is_never_read`:
   catches collections that are written but never read.
  Clippy source:
   <https://rust-lang.github.io/rust-clippy/master/index.html#collection_is_never_read>
- `naive_bytecount`:
   catches slow byte-counting patterns that can use optimized library routines.
  Clippy source:
   <https://rust-lang.github.io/rust-clippy/master/index.html#naive_bytecount>
- `stable_sort_primitive`:
   catches stable sorting of primitive values when unstable sorting is enough.
  Clippy source:
   <https://rust-lang.github.io/rust-clippy/master/index.html#stable_sort_primitive>
- `large_stack_frames`:
   catches functions with large stack frames.
  Clippy source:
   <https://rust-lang.github.io/rust-clippy/master/index.html#large_stack_frames>
- `large_types_passed_by_value`:
   catches large values passed by value where references are likely cheaper.
  Clippy source:
   <https://rust-lang.github.io/rust-clippy/master/index.html#large_types_passed_by_value>
- `redundant_clone`:
   catches clones whose result is unnecessary.
  Clippy source:
   <https://rust-lang.github.io/rust-clippy/master/index.html#redundant_clone>
- `assigning_clones`:
   catches assignment patterns that clone where `clone_from` can reuse allocation.
  Clippy source:
   <https://rust-lang.github.io/rust-clippy/master/index.html#assigning_clones>
