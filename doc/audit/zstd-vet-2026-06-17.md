## What this vet is really deciding

The request came in as "vet facebook/zstd,
" then was sharpened:
 the user suspects
"anything written in C is a lost cause" and is considering rewriting the whole library
and CLI in Rust if the C implementation is "really too bad.
"

So the load-bearing question is not "is zstd nice to use" (it is already in use and
already mostly migrated off the CLI,
 see below).
 The load-bearing question is:

> Is facebook/zstd's C implementation bad enough,
>  on memory-safety grounds,
>  to justify a
> from-scratch rewrite of the library and CLI in Rust?

That reframes the candidate set.
 It is not {zstd vs brotli vs lz4}.
 It is:

- keep the C library (via `node:zlib`'s bundled libzstd,
   or the `zstd`/`zstd-sys` Rust
  crate,
   which also compiles the C);
- adopt an existing pure-Rust implementation for the untrusted path only;
- write our own Rust zstd library and CLI from scratch.

The `choosing-technology` skill is explicit that "write our own" is the last option,
 not
the first,
 and that a hand-rolled module must not be recommended without naming at least
two real packages and the concrete reason each fails.
 This vet names them.

## How zstd is used in this repo today

Gathered before naming any candidate,
 because the attack surface determines how much
memory-safety risk actually reaches this codebase.

Three call sites,
 all already migrated off the external `zstd` CLI binary
(the migration is documented in `doc/decision/zstd-cli-to-node-zlib.md`):

1. `package/figma/kiwi/src/index.ts`,
    `decompressZstd` (line 1197).
   One-shot decompression of the zstd-compressed document section of a Figma `.fig` /
   `.deck` / `.jam` export.
    Calls `node:zlib`'s `zstdDecompressSync` on bytes sliced
   from a downloaded Figma file.
    This is the only path that processes untrusted bytes
   through the C decompressor.
    It runs at dev time (parsing a designer's export),
    not in
   the serving path.
2. `package/ssg/aquati.cat/src/build/compress.ts` plus `compress-lib.ts`.
   Compresses the build's own `dist/` text assets to `.zst` companions at build time via
   `node:zlib`'s `zstdCompressSync` across `node:worker_threads`.
    Input is the repo's
   own generated HTML/CSS/JS/SVG/JSON,
    not attacker-controlled.
    No untrusted input
   reaches the compressor.
3. `package/dev-script/page-weight/src/size.ts`,
    `wireSize` (line 49).
   Stats the `.zst` companion if present and returns its size.
    No compression or
   decompression at all;
    just `stat`.
    No zstd code runs.

The external `zstd` CLI tool declaration has already been removed from `mise.toml` and
`mise.no-env.toml` (verified:
 no `zstd` or `facebook/zstd` entries in either file).
The `@bokuwatch/zstd` optional native module was never a declared dependency and its
fallback path is gone from the Figma parser.

So the repo's residual dependence on facebook/zstd is transitive:
 Node and Bun bundle
libzstd inside `node:zlib`,
 and the `.zst` file format is baked into build output.
 The
C library itself runs (a) on one designer-controlled Figma payload at dev time,
 and (b)
on the repo's own assets at build time.
 There is no internet-facing decompression of
attacker bytes.

## Open-source default and constraint-fit

zstd is BSD-licensed (dual-licensed BSD or GPLv2,
 per `LICENSE` and `COPYING`;
 the BSD
option is permissive and repo-compatible).
 Open-source default satisfied;
 no proprietary
option is on the table.

The hard constraint is format,
 not stack familiarity:
 Figma `.fig` exports carry a zstd
frame,
 so the Figma parser must decode zstd regardless of any preference.
 The ssg
`.zst` companions are served as `Content-Encoding: zstd` to browsers that advertise it
(Chrome 123+,
 Edge 123+,
 Firefox 126+;
 Safari 26+ partial,
 and it falls back to gzip or
brotli when it does not advertise zstd,
 confirmed via caniuse and the MDN
`Content-Encoding` reference).
 The format choice is externally locked for both paths.

### Security and abuse history (direct CVEs)

The direct CVEs against facebook/zstd itself,
 verified against NVD:

- CVE-2019-11922:
   a race condition in the one-pass compression functions prior to
  1.3.8 that could write out of bounds if the caller passed an output buffer smaller
  than `ZSTD_compressBound`.
   Compressor side,
   fixed 1.3.8 (six years ago),
   requires
  caller misuse.
   `node:zlib` allocates via `ZSTD_compressBound` and is not affected.
- CVE-2021-24031:
   the CLI created output files with default permissions and only
  applied input-matching permissions at completion.
   CLI only,
   fixed 1.4.1.
   Library
  unaffected.
- CVE-2021-24032:
   the incomplete-fix sibling of 24031,
   also CLI file permissions,
  fixed 1.4.9.
   Library unaffected.

There are no direct memory-safety CVEs in the libzstd decompressor in the 1.5.
x line.
CVEs that mention "zstd" and memory corruption in 2024 to 2025 are in other projects:
CVE-2024-11477 is a 7-Zip zstd decoder heap overflow (7-Zip's own zstd code,
 not
facebook's);
 CVE-2024-14031 is the Sereal Perl module embedding an ancient pre-1.3.8
zstd;
 CVE-2025-67721 is the Aircompressor Java port;
 CVE-2025-68262 is the Linux
kernel's `crypto/zstd` wrapper double-free,
 not facebook/zstd.
 None of these are the
reference C library.
 This is reported because the search results were noisy and the
distinction matters for the rewrite decision.

The absence of a direct decompressor CVE is not proof of absence of bugs.
 The stronger
signal is continuous fuzzing,
 below.

### Source audit (spot-read)

Public API in `lib/zstd.h` is mature,
 versioned (every entry notes the introducing
version),
 and explicit about untrusted-input contracts.
 The `ZSTD_getFrameContentSize`
doc carries a `@warning` that processing untrusted input requires the caller to validate
the returned size against application limits,
 because attackers may forge an
arbitrarily large value.
 This is the correct guidance and it matches how the Figma
parser is written (it slices a bounded `zstdSize` from a 4-byte little-endian prefix
before decompressing).

The decompressor source is densely guarded.
 Spot-reading `lib/decompress/`:

- `zstd_decompress_block.c` has 64 `RETURN_ERROR_IF` guards and 107 `assert` calls.
  Every block-type,
   literal-size,
   and stream-count branch validates against
  `ZSTD_BLOCKSIZE_MAX`,
   `MIN_CBLOCK_SIZE`,
   and `srcSize` before touching memory.
  Examples:
   `RETURN_ERROR_IF(srcSize < ZSTD_blockHeaderSize, srcSize_wrong, "")`,
  `RETURN_ERROR_IF(litSize > blockSizeMax, corruption_detected, "")`,
  `RETURN_ERROR_IF(expectedWriteSize < litSize, dstSize_tooSmall, "")`.
- `zstd_decompress.c` adds 86 more `RETURN_ERROR_IF` guards and 48 asserts.
- The library uses its own `ZSTD_memcpy`,
   `ZSTD_memmove`,
   `ZSTD_memset` wrappers
  (via `lib/common/zstd_deps.h`) rather than raw libc,
   which bounds the surface for
  accidental misuse.

Module sizes are large (`zstd_decompress_block.c` is several thousand lines),
 which is
expected for a production decompressor and is not itself a smell.
 The error model is
uniform:
 functions return a `size_t` that is either a byte count or an error code
testable with `ZSTD_isError`,
 never a silent failure.

## Alternatives, with concrete rejection reasons

### Compression-format alternatives (for the ssg precompress path)

These are format swaps,
 not memory-safety swaps.
 All four are open-source defaults.

- **brotli** (Google,
   Apache 2.0).
   Better ratio than zstd on text at high quality
  levels and universally supported in browsers (including Safari,
   which does not
  advertise zstd).
   Rejected for this repo because:
   the existing decision doc
  (`doc/decision/zstd-cli-to-node-zlib.md`) already benchmarked zstd at level 19
  against the real `dist/` and chose it deliberately;
   brotli's compressor is far slower
  than zstd at comparable ratios on dynamic content,
   and the ssg path runs at every
  build.
   Brotli is the right pick only if Safari-without-zstd fallback coverage
  matters more than build speed,
   which the existing decision already weighed.
- **lz4** (LZ4,
   BSD).
   Far faster decompression than zstd,
   but a notably worse ratio on
  text (it is the speed extreme of the same family).
   Rejected because the ssg assets
  are precompressed once and served many times,
   so ratio dominates over decompress
  speed,
   and lz4 loses the ratio comparison badly on HTML/CSS/JS.
- **gzip / zlib (DEFLATE)** (BSD-like).
   Universal browser support and a stdlib
  built-in.
   Rejected on ratio:
   zstd level 19 hits 29.80 percent of raw on the real
  `dist/`,
   gzip is materially worse on the same corpus,
   and zstd's decompress speed is
  also higher.
   gzip is only the right pick when maximum legacy client compatibility is
  required,
   which a static blog does not need.
- **xz / lzma** (public domain).
   Best ratio of the set.
   Rejected on decompress speed
  and memory:
   lzma decompression is an order of magnitude slower than zstd and uses far
  more memory,
   which is exactly the tradeoff Arch and Ubuntu made the other way for
  packages.
   For served web assets,
   the ratio edge does not pay back the decode cost.

None of these changes the memory-safety picture,
 because all four are also C libraries
(except the pure-Rust brotli in Firefox,
 which is not packaged for Node).

### Rust implementation alternatives (the actual rewrite question)

- **`zstd` plus `zstd-sys` crates** (gyscos/zstd-rs,
   307M and 313M crates.
  io downloads,
  `zstd-sys` v2.0.16+zstd.
  1.5.7,
   updated 2026-03).
   This is the dominant Rust option.
  Rejected as a memory-safety improvement because it does not provide one:
   `zstd-sys`
  vendors the facebook/zstd C source under `zstd/lib/` and compiles it with the `cc`
  crate (`config.compile("libzstd.a")` in `build.rs`,
   including the
  `huf_decompress_amd64.S` assembly).
   Switching to this crate substitutes the exact
  same C code,
   now behind a safe Rust wrapper.
   The wrapper prevents caller misuse (the
  CVE-2019-11922 undersized-buffer class) but does not eliminate C memory-safety bugs
  inside the library.
   It is a valid option for ergonomic or FFI reasons,
   not for
  memory safety.
- **`ruzstd`** (KillingSpark/zstd-rs,
   49M downloads,
   v0.8.3,
   updated 2026-05-08).
   A
  pure-Rust implementation.
   Its README states its decoder is complete,
   but its
  compressor only implements the Uncompressed and Fastest (roughly level 1) modes;
  Default,
   Better,
   and Best levels,
   plus dictionary compression,
   are unfinished.
   So it
  can replace the Figma decompression call site but cannot replace the ssg compression
  path (which needs level 19).
   It is the only existing option that would give real
  memory safety on the untrusted path,
   and only on that path.
- **Trifecta Tech Foundation `libzstd-rs-sys`** (announced pure-Rust effort,
   not yet at
  parity).
   In progress,
   not production-ready,
   not a current option.

### Write our own Rust library and CLI from scratch

This is the user's proposed option.
 Concrete rejection reasons:

- It rewrites one of the most heavily fuzzed C libraries in existence (eight years of
  continuous OSS-Fuzz,
   see above) as fresh,
   unfuzzed Rust.
   The first several years
  would carry more residual bug risk than the C it replaces,
   not less.
   Rust prevents
  memory-safety bugs at compile time but does not prevent logic bugs (a wrong match
  offset,
   a malformed frame accepted) that corrupt output or mis-size buffers within
  safe Rust.
- It must reimplement the full RFC 8878 format,
   the legacy decoders (v01 through v07,
  present in `lib/legacy/`),
   the dictionary trainer,
   streaming,
   multithreaded
  compression,
   and seekable frames to reach parity with what `node:zlib` already
  exposes.
   The legacy decoders alone are thousands of lines of format-specific C.
- It must reproduce the AMD64 assembly Huffman decoder (`huf_decompress_amd64.S`) or
  accept a large performance regression;
   `ruzstd` already reports 3.5x slower than C
  on highly compressible input.
- The repo's payoff is near zero.
   The only untrusted input that reaches the C
  decompressor is one Figma document at dev time.
   There is no internet-facing
  decompression of attacker bytes.
   A full rewrite buys memory safety on a path that is
  already low-risk and dev-only,
   at the cost of years of engineering and a worse
  encoder than the C one for the build path that actually matters.

## Options ranked

Ranked best to worst for this repo's actual situation.
 The ranking is the answer to the
load-bearing question.

1. **Keep the C library via `node:zlib` (status quo).
   ** Pros:
    zero new work,
    format
   correctness guaranteed,
    eight years of OSS-Fuzz behind it,
    build and round-trip
   verified in this vet,
    already migrated off the CLI.
    Cons:
    the Figma decompression
   path runs C on a downloaded file at dev time.
    Residual risk is low given the narrow
   surface and continuous fuzzing.
2. **Keep C for compression;
    adopt `ruzstd` for the Figma decompression call site
   only.
   ** Pros:
    gains genuine memory safety on the only untrusted path,
    with an
   actively maintained pure-Rust crate whose decoder is complete.
    Cons:
    adds a Rust
   dependency to a TypeScript package (would need a WASM build or a native addon,
   reintroducing the `@bokuwatch/zstd`-shaped problem the migration just removed),
    and
   `ruzstd` is 3.5x slower than C,
    which is irrelevant for one dev-time Figma frame
   but is a real integration cost.
    Worth it only if the Figma input is treated as
   genuinely hostile rather than designer-controlled.
3. **Switch to the `zstd`/`zstd-sys` Rust crate everywhere.
   ** Pros:
    safe-Rust API,
   removes direct C calls from this repo's code.
    Cons:
    no memory-safety gain (it links
   the same C),
    adds a build-time C compilation step,
    and the repo does not currently
   use Rust.
    Net negative.
4. **Full Rust rewrite of library and CLI.
   ** Pros:
    eventually eliminates the C
   memory-safety class entirely,
    if the rewrite reaches parity and gets fuzzed for
   years.
    Cons:
    multi-year effort,
    must reimplement legacy decoders and assembly
   paths to reach parity,
    produces a worse encoder than C for the build path,
    and
   trades proven fuzzed C for unproven Rust.
    Disproportionate to the threat.

Ranking:
 1 > 2 > 3 > 4.
 Adjacent reasons:
 1 beats 2 because the untrusted surface is
one dev-time Figma frame and the integration cost of `ruzstd` in a TypeScript package
outweighs the marginal safety gain;
 2 beats 3 because `ruzstd` at least delivers real
memory safety on the untrusted path whereas `zstd-sys` links the same C;
 3 beats 4
because both eventually link or reimplement C,
 but 3 is a one-line dependency and 4 is
a multi-year rewrite with a worse encoder.

## Recommendation

Do not rewrite zstd in Rust.
 Keep the C library via `node:zlib`.

The premise "anything written in C is a lost cause" does not hold for facebook/zstd
specifically.
 It is the most continuously fuzzed compression library available (first-
party OSS-Fuzz since 2017,
 ASan/Msan/UBSan/Tsan and Valgrind on every PR,
 20-plus
dedicated libFuzzer targets including "decompressor never crashes on fuzzed input"),
its direct CVEs are a compressor race fixed in 2019 and two CLI file-permission bugs,
none of which are untrusted-decompressor memory-safety issues,
 and its decompressor
source is densely guarded.
 The one untrusted path in this repo is a single dev-time
Figma decompression,
 not an internet-facing service.

If,
 despite that,
 the user wants to harden the Figma decompression path specifically,
the proportionate move is option 2:
 adopt `ruzstd` (pure-Rust,
 complete decoder) for
that one call site,
 and leave the ssg compression path on `node:zlib` (where `ruzstd`'s
incomplete encoder cannot go,
 and where the input is the repo's own assets anyway).
That decision should be recorded in `doc/decision/` if taken,
 per the
`choosing-technology` skill.

A full library and CLI rewrite is the last option,
 not the first,
 and is not justified
by the evidence this vet gathered.
