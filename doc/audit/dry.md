# DRY violations audit

> Moved 2026-10-29 by the generic package category elimination
> (`doc/planning/generic-category-elimination.md`);
> paths and names below this note are historical:
> `package/cli/mvm` is now `package/mvm/cli`;
> `package/cli/terminal-exec` is now `package/terminal-exec/cli`;
> `package/cli/vmsync` is now `package/vmsync/cli`.

Generated 2026-05-09 from a mechanical sweep of the 83 packages under `package/`.

This audit covers behaviorally equivalent code or config copies (DRY).
Structural drift across same-class files (package naming,
 README headings,
 version fields,
`private` field presence) is already covered by [the consistency audit](consistency.md);
findings are not duplicated here.

## Scope

In scope:

- Source files reimplementing logic that already lives in a shared workspace package
- Constants redeclared under different names across packages
- Build,
   lint,
   and test config files copy-pasted with drift
- Package manifest fields (`exports`,
   `devDependencies`) repeated verbatim across packages
- Forks where two packages share most of their tree
- Single-occurrence helpers in non-shared packages whose shape is generic
  enough that they should be folded out into a shared module so the next caller
  can reuse them instead of writing their own copy.
   These do not violate DRY today
  but encode the same future-DRY-violation risk:
   the second caller is going to
  reinvent them.
   Section:
   "Reusable utilities awaiting extraction".

Excluded by construction:

- Files generated by [`file-enforcer.config.ts`](../../file-enforcer.config.ts):
  `CLAUDE.md`,
   `mise.toml` at repo root,
   `forbidden-strings.local.txt`,
  `forbidden-strings.append.local.txt`,
   `.factory/skills/*/*.md`,
   `.claude/skills/*/*.md`
- `package/test-fixture/*` where duplicate inputs are the point of the fixture
- Cross-runtime `*.browser.ts` / `*.node.ts` variants where the platform forces separate code
- `pnpm-lock.yaml` and other lockfiles

## Methodology

Per category,
 files were enumerated,
 hashed with `sha256sum`,
 and bucketed by hash to find
exact byte-level duplicates.
 Near-duplicates were sampled and diffed pairwise.
For source-level duplication,
 `rg` queries enumerated function definitions,
 type aliases,
const declarations,
 regex patterns,
 and shared filenames;
 the most-frequent occurrences
were inspected line by line.

The "Reusable utilities awaiting extraction" section was generated separately:
candidate function names were enumerated by utility-shape patterns
(`format*`,
 `parse*`,
 `escape*`,
 `normalize*`,
 `encode*`,
 `decode*`,
 `is*`,
`require*`,
 `ensure*`,
 `truncate*`,
 `chunk*`,
 etc.),
 occurrence counts captured,
and each candidate's body inspected to confirm primitive-in / primitive-out shape
and absence of package-specific dependencies.
 The current `module/es` taxonomy
(via `find package/module/es/src -type d`) was checked first so candidates already
covered by an existing export were excluded.

Every finding cites file paths and where applicable line numbers,
 so claims can be
verified by opening the file.
 Numeric counts in headings are exact occurrence counts at
audit time,
 not estimates.

## Findings

The findings are grouped:
 build configuration first,
 then large structural duplication
(package forks),
 then function-level duplication,
 type-level duplication,
 constant-level
duplication,
 file-template duplication,
 and miscellaneous patterns.

### Build configuration

#### Three packages declare per-platform mise tasks without matching config files

**Resolved 2026-05-09**:
 each package's bare `tsdown.config.ts` was renamed to the
platform-suffixed form matching its declared mise tasks.
`package/module/hyperscript/` now has `tsdown.browser.config.ts` only;
`package/figma/{kiwi,penpot}/` now have both `tsdown.browser.config.ts` and
`tsdown.node.config.ts`.
 `dist/final/{neutral,node}/` populates accordingly.

`mise.toml` files in three packages declare `build:js:browser` and/or `build:js:node`
task children whose root templates pass `--config tsdown.<platform>.config.ts`,
 but the
matching config file does not exist on disk:

- `package/module/hyperscript/mise.toml` declares `build:js:browser`;
   only
  `tsdown.config.ts` is present
- `package/figma/kiwi/mise.toml` declares `build:js:browser` and
  `build:js:node`;
   only `tsdown.config.ts` is present
- `package/figma/to-penpot/mise.toml` declares `build:js:browser` and
  `build:js:node`;
   only `tsdown.config.ts` is present

Empirical effect (verified by inspecting `dist/final/`):
 each contains only `neutral/`
and `types/`,
 never `node/` or `browser/`.
 The declared task names misrepresent what the
build produces.

Suggested resolution:
 drop the unused per-platform task children from the three
`mise.toml` files,
 or add the matching suffixed config files if the per-platform output
is wanted.

- `package/webapp-productivity/done-h-css-test/tsdown.client.config.ts`
- `package/webapp-productivity/doodle-widget/tsdown.client.config.ts`
- `package/webapp-productivity/syllable-break-demo/tsdown.client.config.ts`
- `package/webapp-edu/paper2vn/tsdown.client.config.ts`
- `package/ssg/aquati.cat/tsdown.client.config.ts`
- `package/webapp-content/messages-demo/tsdown.client.config.ts`

Out of scope for a single fix,

### Function-level duplication

#### `resolvePort` is reimplemented in five files

Verbatim 12-line bodies (one variant uses env only):

- `package/webapp-forge/server/src/index.ts`
- `package/webapp-content/messages-demo/src/server.ts`

`package/module/es/src/server/resolve-port.ts` (or similar).

#### `getArgumentValue` (or `getFlag`) is reimplemented in five files

Four `lib/args.ts` files declare an identical `getArgumentValue(name: string)`
helper that scans `process.argv` for `--name=value`:

- `package/webapp-forge/server/src/lib/args.ts`
- `package/webapp-productivity/done/src/lib/args.ts`
- `package/webapp-productivity/done-h-css-test/src/lib/args.ts`
- `package/webapp-content/messages-demo/src/lib/args.ts`

A fifth file,
 `package/webapp-forge/stress/src/scenarios/shared.ts:getFlag`,
declares the same logic under a different name (`getFlag` instead of
`getArgumentValue`).

The `lib/args.ts` docblocks even cite each other as "mirrors",

is acknowledged.

Notable:

`webapp-forge/`.
 The fact that `stress/src/scenarios/shared.ts` already exists as a
local extraction but `webapp-forge/server` does not import from it shows the
within-`webapp-forge/` boundary is itself porous.

Suggested home:
 `package/module/es/src/cli/get-argument-value.ts`.

- `package/dev-script/task-util/src/depends-resolve-glob.ts:splitGlob`

Both use a `GLOB_META` regex to find the first metacharacter,
 then partition.
 Tuple
shapes differ slightly (file-enforcer also returns the `originalPrefix`),
 but the
core logic is the same.
 Any package that needs to plumb glob patterns through `cwd`
boundaries will want this;
 the next caller will write a third copy.

Suggested resolution:
 extract to `module/es/path/glob.ts` (sibling to the existing
`path/` helpers).
 Both call sites import;
 the file-enforcer site adds the
`originalPrefix` post-processing locally.

#### `round1` (round to one decimal place) in two places

`package/test-fixture/file-enforcer-perf/src/{validate-benchmarks,bench-in-container}.ts`
both define `round1(value): number => Math.round(value * 10) / 10`.
 Same body,
 no
divergence.
 While `test-fixture/*` is excluded from the broader DRY scope,
 this
function is shape-generic enough that it should leave the fixture and live in
`module/es`:
 any package that prints fractional metrics will write its own copy
otherwise.

Suggested resolution:
 move to `module/es/types/t number/...` (the taxonomic location
for number utilities).
 Generalize to `roundTo(value, decimals)`;
 provide
`round1`/`round2` as named conveniences if the call site readability matters.

#### `encodeS3Key(key)` (per-segment URI encoding) in one place

`package/webapp-forge/server/src/storage/adapter-s3.ts:encodeS3Key` URI-encodes each
`/`-separated segment of an S3 key while preserving the separator.
 Generic enough
to belong outside the S3 adapter;
 the same operation works for any path-shaped
identifier that needs URL-safe encoding (file paths,
 CDN keys,
 route segments).

Suggested resolution:
 extract to `module/es/path` (sibling to `trim`,
 `ensure`,
`empty`).
 The S3 adapter imports.

#### `escapeString` in one place

`package/dev-script/file-enforcer/src/package/mise.generate-index.ts:escapeString`
escapes `\` and `'` for embedding into single-quoted TypeScript string literals,
the canonical operation for codegen tools that emit TS source.
 Single caller today,
but file-enforcer is one of several codegen tools (forbidden-strings has
`escapeResharpOnlyMeta`;
 the messages-demo composer emits HTML);
 the next codegen
package that emits TS will reinvent this.

Suggested resolution:
 extract to `module/es/types/t string/...` next to other string
helpers.
 Provide `escapeForSingleQuoted` and `escapeForDoubleQuoted` variants since
the escape sets differ.

#### `withTimeout(promise)` browser variant alongside `module/es` async variant

**Resolved 2026-05-09**:
 `storage-probe.ts` now composes with the shared
`withTimeout` from `@monochromatic-dev/module-es/with-timeout`.
 A small
`capProbe({probe, label})` helper wraps the shared utility in a try/catch so
timeout or backend rejection still maps to `false`.
 The local timer wiring is
deleted.
 Verified by `mise run //package/webapp-content/messages-demo:build`
producing the firefox140 client bundle without warnings.

`package/webapp-content/messages-demo/src/client/storage-probe.ts:withTimeout`
implements timeout-via-`Promise.race`-with-`setTimeout`.
 The codebase already exports
`withTimeout` from `@monochromatic-dev/module-es/with-timeout` (verified at
`package/module/es/src/types/t object/t promise/f/t object/withTimeout/r a/p p/index.ts`).
The local copy hardcodes a `PROBE_TIMEOUT_MS` and resolves with `false` instead of
rejecting;
 it is a domain-specific specialization,
 but it does so by reimplementing
the timer wiring rather than by composing with the shared utility.

Suggested resolution:
 rewrite the local site to compose with the shared
`withTimeout`:
 `await withTimeout({ promise, ms: PROBE_TIMEOUT_MS, label: 'probe' })
.catch(() => false)`.
 The local function declaration goes away;
 the timer logic
stays in one place.

#### `cli/mvm/src/spawn.ts` and `cli/vmsync/src/spawn.ts` are near-byte-identical

`spawn({command, args}): Promise<string>`,
 11-line diff between two 50-line files
(46 vs 52).
 The diff is one example string in a docblock and one log-tag rename.
Both wrap `nano-spawn` with the codebase's tagged-logger pattern.

The audit's existing function-level section captures `mcp/{nvim, mvm}` already
factor through `@monochromatic-dev/mcp-stdio`;
 the cli/{mvm,
 vmsync} pair has no
analogous shared base.
 This is both a reusable-utility candidate and a DRY violation
the function-level scan missed because the function is named `spawn` (high
collision rate,
 scan dropped to noise).

Suggested resolution:
 ship a `nanoSpawnTagged({command, args, logger}): Promise<string>`
helper:
 either as a new tiny package (e.g. `module/spawn-tagged`) or as an export
from `module/logger` since the value-add over raw `nano-spawn` is purely the tagged
log-line.
 Both CLI packages import.

#### `groupBy*` family in five places, all reducing to `(items, keyFn) => Record<key, items[]>`

Five separate `groupBy`-shaped functions across two packages,
 each implementing the
same one-pass partition-by-key with different key types and result shapes:

- `package/ssg/aquati.cat/src/lib/content-group.ts:groupByLang(posts)`:
  delegates to `Map.groupBy`,
   returns `Partial<Record<Locales, Post[]>>`
- `package/ssg/aquati.cat/src/lib/content-group.ts:groupByName(posts)`:
  delegates to `Map.groupBy`,
   returns `Record<string, Post[]>`
- `package/ssg/aquati.cat/src/lib/content-group.ts:groupByTag(posts)`:
  walks `allTags(posts)`,
   returns `Record<string, Post[]>`
- `package/ssg/aquati.cat/src/lib/content-group.ts:groupByLangThenTag(posts)`:
  composition of the previous two,
   returns `Partial<Record<Locales, Record<string, Post[]>>>`
- `package/desktop-daemon/editord/src/client/inlay/group-by-line.ts:groupByLine<T>({items, keyFn})`:
  generic,
   returns `Map<number, T[]>`,
   hand-rolled (does not use `Map.groupBy`)

The `ssg-test` quartet uses the stdlib `Map.groupBy` and just wraps it in a
`Object.fromEntries` shim to match the per-call shape.
 The `editord` site predates
or ignores `Map.groupBy` and writes its own loop.
 Different result containers
(`Record` vs `Map`),
 but the same operation underneath.

Suggested resolution:
 ship a single `groupBy<T, K>({items, keyFn}): Map<K, T[]>` from
`module/es` (returning `Map` rather than `Record` so non-string keys work).
 Provide
a thin `groupByToRecord` companion for the `Record<string, T[]>` callers.
 The five
sites collapse to four `groupBy(...)` calls plus one `groupByToRecord` call;
 each
keeps its own keyFn but drops the shared loop body.

#### Cross-cutting note: where these utilities should land

`module/es` is the natural home for type-level and primitive-level helpers
(formatBytes,
 parseMemoryToBytes,
 isDefined,
 randomId,
 formatMs,
 formatNumber,
concatBytes,
 round1,
 encodeS3Key,
 escapeString,
 splitGlob,
 ensureDir,
 groupBy).
`module/test` is the home for the test-only `uniqueId({ prefix })`.
 `module/dom`
gets `requireElement` and `readPageData`.
 The spawn-tagged helper plausibly lives in
`module/logger` (since the value-add is the tagged log line) or as its own tiny
package alongside other I/O-shaped helpers.

A useful test for whether each fold-out is right-sized:
 does the helper contain any
package-specific assumption (a hardcoded constant tied to the source package,
 an
import from the source package,
 a call to a logger tagged with the package name)?
If yes,
 the extraction needs a config parameter;
 if no,
 the extraction is a direct
move.
 Most candidates above are direct moves.

 but the duplication is the consequence of an
existing shared base.
 Listed here so they are not flagged in future audits.

#### `tsdown.*.config.ts` per-package files (43 total)

32 are byte-identical one-line re-exports of one of three bases in
`@monochromatic-dev/config-tsdown`:

- 20 re-export `.node.ts`
- 10 re-export `.ts` (neutral)
- 2 re-export `.client.ts`
- 11 override the base with a per-package entry list (each importing the relevant base
  via `import base from '@monochromatic-dev/config-tsdown/.node.ts'` or similar)

The remaining structural duplication is forced by tsdown's CWD-relative config lookup.

#### `tsconfig.json` per-package files (85 total)

68 are byte-identical extensions of `@monochromatic-dev/config-typescript/dom`:

- 57 with `{ "extends": "@monochromatic-dev/config-typescript/dom" }`
- 6 with `{ "extends": ..., "compilerOptions": {} }` (empty block)
- 5 with `{ "extends": ..., "include": [] }`

The 6-file empty-block cluster is a stylistic minor inconsistency worth normalizing
during a future drive-by.

#### `module/es` barrel re-export files

`package/module/es/src/types/...` is organized as a deeply nested directory tree
following the package's own taxonomy.
 Each level has a one-line `index.ts` that
re-exports the next level.
 Across the tree,
 several one-line barrel patterns recur:

- `export * as sync from './r s/index.ts';`:
   52 files
- `export * as positional from './p p/index.ts';`:
   51 files
- `export * as type from './t/index.ts';`:
   27 files
- `export * as from from './f/index.ts';`:
   24 files
- `export * as named from './p n/index.ts';
  export * as positional from './p p/index.ts';` (16 files)

These are byte-identical because they encode a structural relationship in the
directory tree (a level always has the same set of subfolders).
 The duplication is
forced by TypeScript's directory-as-namespace convention combined with module-es's
naming taxonomy (`t` = type,
 `f` = function,
 `r s` = return sync,
 `p p` = positional
parameters,
 etc.,
 as documented in module-es's README).

Listed as a positive finding (already-shared category) so the next audit does not
re-flag them.
 A code generator could produce them,
 but the gain is small.

#### Per-package `mise.toml` files (81 total)

The largest cluster of 7 byte-identical files contains only `extends = "..."` re-exports
of root-level task templates.
 17 packages share one of two stub shapes (7 + 7 + 3).
 The
duplication is structural and unavoidable:
 each package needs to opt into the task
templates it wants from the root.
