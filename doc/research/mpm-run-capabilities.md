# mpm.run capabilities versus mise for this repo

Research question:
can `mpm.run` (Meta Package Manager,
the `mpm` CLI,
PyPI
`meta-package-manager`) replace [mise][mise-home] for toolchain management in this
repository,
and how?

Short answer:
**no**,
not as a drop-in replacement.
`mpm` is a system-scoped
inventory and upgrade orchestrator that wraps other package managers,
including
[mise itself][mpm-mise].
It has no per-project tool manifests,
no lockfile with
resolved artifacts,
no tool options (OS filters,
postinstall hooks,
cargo
features),
no environment activation,
no secrets,
and no task runner.
It could
sit beside mise as a cross-manager audit and upgrade layer.

## What mpm is

`mpm` is a Python CLI ([PyPI package `meta-package-manager`][mpm-pypi]) that
discovers the package managers already present on a machine and drives them
through one
vocabulary:
`installed`,
`outdated`,
`search`,
`install`,
`remove`,
`upgrade`,
`sync`,
`cleanup`,
`doctor`,
plus snapshots (`dump`/`restore`) and SBOM export
([CLI reference][mpm-cli],
clone `meta_package_manager/cli_explore.py`,
`cli_maintenance.py`,
`cli_snapshots.py`,
`cli_sbom.py`).
Its own framing is
"like yt-dlp,
but for package managers instead of videos" ([home][mpm-home]).

The primary use case is fleet maintenance:
snapshot every package on a machine
to one TOML manifest,
restore it on a new machine,
list and upgrade everything
outdated across all managers at once,
with a release-age cooldown as a
supply-chain guard ([home][mpm-home],
[dump docs][mpm-dump]).

The manifest is a machine inventory,
per manager,
one entry per package with the
installed version as the value ([dump docs][mpm-dump],
section `TOML manifest`):

```toml
# Generated by mpm 8.1.2.
# Timestamp: 2026-10-12T10:30:00.000000+00:00.

[brew]
ack = "3.3.1"
```

`mpm` explicitly declines project-scoped dependency managers
([unsupported managers][mpm-unsupported]):
"Tools that resolve
dependencies inside a working tree are out of scope today" (clone
`docs/unsupported.md:726`,
with `ManagerScope.PROJECT` and issue 1725 as a future
extension point).

## Capability answers

### Committed per-project manifest and machine provisioning: partial

- **Provisioning exists**:
  `mpm restore <file>` installs every package a TOML
  manifest lists,
  and several manifests replay in one run
  ([dump docs][mpm-dump],
  `Round-trip: switch systems`;
  clone
  `meta_package_manager/cli_snapshots.py:414`).
- **A manifest can be committed per project**,
  since the file path is an explicit
  argument,
  but `mpm` gives it no project semantics.
  Nothing reads it on
  directory entry,
  nothing scopes installs to the project,
  and the installed
  state is **machine-global**:
  each backend installs into its own global store
  (`brew` Cellar,
  `npm --global`,
  `cargo install` into `~/.cargo`,
  `pipx`),
  and
  `mpm` keeps only user-level configuration (`~/.config/mpm/`,
  or a `[tool.mpm]`
  section in `pyproject.toml` holding CLI options,
  not a tool list)
  ([configuration][mpm-config],
  section `Location`).
- The `mise` manager wrapper states the scope model outright:
  "mpm is
  system-scoped,
  so this wrapper reports every tool version present on disk
  regardless of which `mise.toml` (global or project) requested it.
  Project-pinned
  versions are not surfaced as a separate scope" (clone
  `meta_package_manager/managers/mise.py:40-43`).

### Version pinning granularity: partial

- **Exact versions,
  yes where the backend supports them.**
  The specifier grammar
  is `package_id@version`,
  `@scope/name@version`,
  or a pURL
  `pkg:npm/left-pad@3.7` (clone `meta_package_manager/specifier.py:41`,
  `:238-267`).
  `mpm install jq@1.7.1` is a documented example (clone
  `meta_package_manager/cli_maintenance.py:464`).
- **Floating channels are opaque strings,
  not mpm semantics.**
  A version is
  passed through verbatim;
  the validator accepts any token with an integer in it
  or a single word (clone `meta_package_manager/version.py:747-760`),
  so
  `latest`,
  `nightly`,
  `21.0.4-tem`,
  `0.15.2` and `b9829` are all legal spec
  strings.
  Whether they mean anything is up to the wrapped manager:
  `asdf`
  forwards `version or "latest"` (clone `meta_package_manager/managers/asdf.py:212-224`),
  `sdkman` forwards the identifier (`sdk install java 21.0.4-tem`,
  clone
  `meta_package_manager/managers/sdkman.py:195-201`),
  `mise` builds
  `tool@version` (clone `meta_package_manager/managers/mise.py:200-212`).
- **Many managers drop the pin with only a warning.**
  `@version_not_implemented`
  logs "does not implement version parameter.
  Let the package manager choose the
  version."
  and installs anyway (clone `meta_package_manager/capabilities.py:373-387`).
  It decorates `install` in `npm` (clone
  `meta_package_manager/managers/npm.py:312-324`),
  `pipx` (clone
  `meta_package_manager/managers/pipx.py:291-305`),
  `pip`,
  `pnpm`,
  `nix` and
  others.
  Every config-defined manager (see the next section) warns
  "Configuration-defined managers do not support version pinning."
  (clone
  `meta_package_manager/definitions.py:1199-1205`,
  `:536-537`).
- **No ranges.**
  There is no `>=1.2`,
  `^1`,
  `~1.2` grammar anywhere in the
  specifier or version modules;
  the version token is a string forwarded to the
  backend.

### Lockfile and reproducible reinstall: partial

- `mpm dump packages.toml` records resolved installed versions per manager,
  and
  is aliased `mpm lock`,
  `mpm freeze`,
  `mpm snapshot` ([dump docs][mpm-dump];
  clone `meta_package_manager/cli_snapshots.py:148-245`).
  `mpm dump
  --update-version` refreshes entries and `--merge` adds new ones.
- `mpm restore` reinstalls each entry with the recorded version:
  it builds
  `pkg:<manager>/<id>@<version>` per row (clone
  `meta_package_manager/cli_snapshots.py:463-470`).
- **It is not a `mise.lock` equivalent.**
  There is no resolution step,
  no
  resolved download URL,
  no checksum,
  no per-platform artifact table,
  and no
  transitive closure.
  Reinstall fidelity is only as good as each backend's
  version support,
  which the previous section shows is missing for npm,
  pipx,
  cargo and every config-defined manager.
  The Brewfile export is explicitly
  version-less:
  "TOML pins versions for `mpm restore`,
  while Brewfile lets
  Homebrew Bundle resolve to the latest version of each entry at install time"
  (clone `docs/dump.md:140`).
- Cross-manager matching during restore is a recorded todo:
  "Implement a best
  matching strategy,
  across package managers of different kinds" (clone
  `docs/dump.md:87-89`).

### Multiple installer backends and backend selection: partial

Routing exists,
in a different shape from mise's `cargo:`/`npm:` prefixes:

- **Manifest sections name the manager**:
  `[npm]`,
  `[cargo]`,
  `[pipx]` (clone
  `meta_package_manager/cli_snapshots.py:457-463`).
- **CLI selectors**:
  `mpm --brew install jq`,
  `mpm --no-rustup`,
  and
  `--manager`-style include/exclude selectors ([home][mpm-home],
  section
  `Features`;
  [rustup manager page][mpm-rustup],
  section `Configuration`).
- **pURL specifiers**:
  `mpm install pkg:npm/left-pad` ties a package to one
  manager (clone `meta_package_manager/cli_maintenance.py:464-472`).
- **Untied names fall through a priority search**:
  "Installation will be
  attempted with each manager,
  in the order they were selected" (clone
  `meta_package_manager/cli_maintenance.py:490-492`),
  for example
  `brew > cask > composer > gem > mas > npm > pip > pipx > vscode > yarn`
  ([install docs][mpm-install],
  section `Self-bootstrapping`).

Coverage for the tool classes this repo uses (see the mapping section):
`mise`,
`asdf`,
`rustup`,
`sdkman`,
`zvm`,
`pyenv`,
`ghcup`,
`juliaup`,
`volta`,
`nix` and
`brew` handle toolchains;
`cargo`,
`npm`,
`pnpm`,
`yarn`,
`bun`,
`pipx`,
`uv`,
`uvx`,
`pip`,
`conda`,
`mamba`,
`micromamba` and `pixi` handle packages;
`stew`
and `bin` handle GitHub-release binaries ([manager matrix][mpm-managers]).
The
`cargo` manager is plain `cargo install` with no `outdated` and no `upgrade`
(clone `meta_package_manager/managers/cargo.toml:6-8`,
`:42`),
and there is **no
cargo-binstall integration** (no occurrence in the clone).
There is **no aqua
registry backend and no vfox backend** (no occurrence of either in the clone's
source or docs).

### Tool options (OS filters, postinstall, cargo features, renaming): no

- The manifest row is `id = "version"` only (clone
  `meta_package_manager/cli_snapshots.py:463-470`);
  there is no per-package
  option table.
- Nearest capability is per-manager configuration,
  not per tool:
  `[mpm.overrides.<id>]` accepts `cli_names`,
  `cli_search_path`,
  `cooldown_policy`,
  `dry_run`,
  `extra_env`,
  `plan`,
  `post_args`,
  `pre_args`,
  `pre_cmds`,
  `requirement`,
  `stop_on_error`,
  `sudo`,
  `timeout`,
  `unmaintained`,
  `version_cli_options`,
  `version_regexes`,
  plus `extra_args` per operation
  (clone `meta_package_manager/definitions.py:211-229`,
  `:517`).
  `platforms` is
  deliberately not overridable and is a manager-level classification.
- No per-package `os = ["linux"]` filter,
  no postinstall hook commands,
  no cargo
  feature flags (`features = "unix"` is unexpressible),
  no installed-binary
  renaming or linking.

### Environment activation: no

`mpm` installs packages and otherwise gets out of the way.
It has no shims,
no
`env` table,
no activation or deactivation,
and no export of tool-provided
variables such as `ANDROID_HOME`.
The `shell_env` module exists for the opposite
direction:
importing the login shell's environment into an `mpm` run started
outside a terminal (clone `meta_package_manager/shell_env.py:17-30`),
so
managers installed under the home directory are visible.
Wrapped managers that
do activation (`mise`,
`volta`,
`pyenv`,
`asdf`) keep doing it on their own;
`mpm`
does not orchestrate it.

### Secrets integration: no

No equivalent of mise's built-in rops/sops/age decryption exists,
and nothing in
the docs,
configuration schema or CLI mentions secrets management.
This is out
of scope for `mpm`.

### Task running: no

The command tree is `managers`,
`installed`,
`outdated`,
`orphans`,
`search`,
`which`,
`config-template`,
`install`,
`upgrade`,
`remove`,
`sync`,
`cleanup`,
`doctor`,
`dump`,
`restore`,
`sbom` (clone `meta_package_manager/cli_explore.py`,
`cli_maintenance.py`,
`cli_snapshots.py`,
`cli_sbom.py`).
There is no `run`
command and no task concept.

### Upgrade semantics: partial

- `mpm upgrade --all` is the flagship operation:
  every outdated package of every
  manager,
  per-manager `✓`/`✘` trail and a closing summary ([home][mpm-home];
  clone `meta_package_manager/cli_maintenance.py:693-800`).
- **Release-age cooldown exists**:
  `[mpm.cooldown] period = "1 week"` with
  `policy = "enforce"` (default) or `"best-effort"`,
  plus the one-run `--cooldown`
  keywords ([configuration][mpm-config],
  section `Release-age cooldown`).
  Managers
  that cannot honor the window are skipped during install and upgrade (fail-closed)
  by default (clone `docs/configuration.md:80`).
- **No pin or hold verb.**
  The comparison table leaves mpm's `Pin / Unpin
  version` cell empty ([benchmark][mpm-benchmark],
  operation rows).
  Upgrades can
  be narrowed to named packages (`mpm upgrade curl jq`) or to selected managers
  (`mpm --brew upgrade --all`),
  and the cooldown holds back fresh releases,
  but
  nothing freezes one project's pinned tool set while the rest of the machine
  upgrades.
- Note the exit contract:
  `upgrade --all` is a maintenance command,
  so "a failed
  manager gets a ✘ and the exit stays 0" (clone `meta_package_manager/cli.py:67-72`).

### CI support: yes

- **Standalone executables** for `linux-x64`,
  `linux-arm64`,
  `macos-x64`,
  `macos-arm64`,
  `windows-x64` and `windows-arm64`,
  compiled at each release
  ([binaries][mpm-binaries],
  section `ABI targets`).
  Binaries and Python packages
  are signed with GitHub Artifact Attestations (SLSA v1) and verify with
  `gh attestation verify` ([install][mpm-install],
  section `Release
  verification`).
  The docs advertise them as "useful for CI/CD pipelines running
  on minimal images" ([home][mpm-home]).
- Python installs work through `uv tool install meta-package-manager` or
  `pipx`,
  on Linux,
  macOS and Windows ([install][mpm-install]).
- **No container images** are published (nothing in `docs/` or `packaging/`
  references one;
  `packaging/` holds Alpine,
  Chocolatey,
  Guix,
  MacPorts,
  Nix,
  openSUSE and PPA recipes).
  **No dedicated GitHub Action** and no `mpm`-level
  cache directory for CI to cache;
  each wrapped manager keeps its own caches,
  clearable via `mpm cleanup`.

### dump/restore round-trip fidelity: partial

- Exact-version restore is attempted for every row (clone
  `meta_package_manager/cli_snapshots.py:463-470`),
  and `mpm install`/`restore`
  exit `1` when a package fails to install (clone
  `meta_package_manager/cli.py:67-69`).
- **A pin a manager cannot express is silently downgraded to "whatever the
  manager resolves"**,
  with only a WARNING line (clone
  `meta_package_manager/capabilities.py:380-386`,
  `meta_package_manager/definitions.py:1199-1205`).
  The run still counts the
  package as installed.
- **A tool whose manager is absent on the new machine is dropped without failing
  the run.**
  `restore` iterates only managers that implement `install` and are
  present (clone `meta_package_manager/cli_snapshots.py:418-421`);
  unavailable
  managers are filtered with `drop_not_found: bool = True` and a
  `Skipped: {reason}.` line logged at INFO,
  or DEBUG when the selection was
  implicit (clone `meta_package_manager/pool.py:441`,
  `:538-545`),
  both below the
  default WARNING verbosity.
  Unrecognized sections are ignored at INFO (clone
  `meta_package_manager/cli_snapshots.py:453-455`).

### Platform support: yes

"Runs on macOS,
Linux,
Windows,
FreeBSD,
NetBSD,
OpenBSD,
illumos and Solaris,
with standalone executables for the first three" ([home][mpm-home]);
the binary
matrix now covers six ABI targets ([binaries][mpm-binaries]).
Each wrapped
manager carries its own platform gate,
so the usable surface is the
intersection.

  `license` file is
  GPL v2 text).
- **Latest release**:
  `v8.2.0` on 2026-10-25;
  about 25 GitHub releases between
  2026-04-09 and 2026-10-25 (roughly weekly),
  repository pushed 2026-10-26
  (`gh api repos/kdeldycke/meta-package-manager` and its `releases` list).
- **Open issues**:
  22 open items,
  11 of them non-PR issues,
  none labelled
  critical or blocker;
  the one closest to this repo's needs is issue 1725
  "Support manager contexts for multi-scope and multi-binary discovery",
  the
  same project-scope work named in the todo (clone `docs/unsupported.md:728-730`).
- **Popularity and history**:
  624 stars,
  project created 2016-08-17;
  a single
  named maintainer (Kevin Deldycke) with sponsorship,
  shipping manager wrappers,
  two desktop frontends and a documentation site in the same cadence.
- **Failure semantics**:
  three exit contracts (clone
  `meta_package_manager/cli.py:67-72`):
  action commands (`install`,
  `remove`,
  `upgrade <packages>`,
  `restore`) collect per-package failures and exit 1;
  maintenance commands (`sync`,
  `cleanup`,
  `upgrade --all`) are best-effort and
  exit 0 with `✘` markers;
  `doctor` exits 1 when a diagnostic reports problems;
  `--zero-exit` opts out of both gates.
  **Backends can and do skip work quietly**:
  dropped version pins (WARNING),
  absent managers (INFO or DEBUG),
  unrecognized
  manifest sections (INFO).
  A CI consumer that treats exit 0 as "the manifest is
  fully applied at its pinned versions" would be wrong.

targets = "aarch64-linux-android,x86_64-linux-android" }`.

- **No.** The rustup manager models toolchains only and states why components
  cannot be packages:
  "The packages here are toolchains,
  not components" (clone
  `meta_package_manager/managers/rustup.toml:5-25`).
  No component list,
  no
  target list,
  nothing comparable to mise's `components` and `targets` keys.

### Postinstall-hooked tools

`cargo:monochromatic-git-policy-cli` with `os = ["linux"]` and a `postinstall`
that links `cli-git-native` as `git` in `.cache/cli-git-bin`.

- **No.** No postinstall hook,
  no per-package OS filter,
  no binary linking
  feature.
  The per-manager `pre_cmds` / `extra_args` knobs (clone
  `meta_package_manager/definitions.py:211-229`) attach to every invocation of a
  manager,
  not to one package's install.

## Feasibility verdict

`mpm` cannot replace mise for this repository.
It answers a different question:
"what is installed on this machine,
across every package manager,
and how do I
upgrade or clone it",
not "which tool versions does this project need,
resolved
and recorded".
The repo's own config leans on the second question continuously
(`mise.toml` `[tools]`,
`mise.lock`,
`[env]`,
tasks),
and `mpm` covers almost
none of it.

### Hard gaps versus what mise provides today

1. **Per-project tool manifest semantics.**
   `mpm` is machine-scoped by design
   (clone `meta_package_manager/managers/mise.py:40-43`,
   `docs/unsupported.md:726`);
   no `mise.toml` equivalent,
   no auto-install on
   directory entry,
   no trust model,
   no per-project state.
2. **Lockfile fidelity.**
   No resolved URLs or checksums,
   no per-platform
   resolution like `mise.lock`,
   and pinned versions are silently dropped by npm,
   pipx,
   cargo and every config-defined manager (clone
   `meta_package_manager/capabilities.py:380-386`).
3. **Rust components and cross targets.**
   `clippy`,
   `rust-src`,
   `llvm-tools`,
   `rustc-dev` and `aarch64-linux-android` are unexpressible (clone
   `meta_package_manager/managers/rustup.toml:5-25`).
4. **Cargo backend quality.**
   No cargo-binstall prebuilt resolution (plain
   `cargo install`,
   no `outdated`/`upgrade`),
   no `features = "unix"`,
   no version
   pins (clone `meta_package_manager/managers/cargo.toml:6-12`).
5. **Tool options.**
   No per-tool `os` filters,
   no postinstall hooks,
   no binary
   renaming or linking;
   the git-policy `git` link step has no home.
6. **Environment activation.**
   No `env`,
   no shims,
   no exported `ANDROID_HOME` or
   `_.path`-style PATH composition,
   no `_.file` secrets file (compare
   `mise.toml` `[env]` in this repo).
7. **Secrets.**
   No rops/sops/age integration at all.
8. **Task running.**
   No `run` command,
   so `mise run` (the repo's only task
   runner) has no counterpart.
9. **GitHub-release tag pins.**
   `llama.cpp = "b9829"` style pins have no route;
   no aqua registry backend and no vfox backend exist.
10. **Android SDK provisioning.**
    No `sdkmanager` or vfox wrapper,
    and no tool
    options model in which to describe SDK components.

### What mpm could still do alongside mise

- Cross-manager `installed` / `outdated` / `orphans` / `duplicates` audits and
  SBOM export (`mpm sbom`) across the distro,
  `brew`,
  `cargo`,
  `npm`,
  `pipx` and
  `uv` layers this machine also carries.
- Fleet-wide `mpm upgrade --all` with the release-age cooldown,
  as a
  supply-chain guard that mise's `minimum_release_age` only covers for
  mise-managed tools.
- Machine cloning for dotfiles-style provisioning (`mpm dump` on one box,
  `mpm restore` on the next),
  with the fidelity caveats above.
- CI bootstrap:
  a single attested standalone executable per OS/arch,
  no Python
  needed.
- Notably,
  `mpm` can wrap **mise itself** as one manager among many (clone
  `meta_package_manager/managers/mise.py`),
  which is the natural composition:
  keep `mise.toml` and `mise.lock` as the project toolchain source of truth,
  and
  let `mpm` observe and upgrade the machine around it.

Ranking of the two roles:
**mise stays** as the project toolchain manager;
**mpm joins at most** as a system-level inventory and upgrade layer,
and only if
the repo wants that layer.
