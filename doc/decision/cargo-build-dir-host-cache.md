# Cargo build intermediates live in the host cargo cache, not in each package's `target/`

Records a host-level Cargo setting that changes where every Rust package in this repository puts its
intermediate build artifacts.
Future sessions consult this before assuming a package's `target/` directory holds a full build tree,
before using `git clean -X` to reclaim Rust build space,
and before proposing to move this setting into the repository.

This document is appended to,
 not rewritten.
When new constraints force re-evaluation,
 mark this decision superseded;
 do not delete it.

## Status

Accepted 2026-09-19.
The user set it directly in `~/.cargo/config.toml` on this machine and asked for it to be recorded here.
Nothing in this repository sets it,
 and no repository task depends on it being set.

## The setting

```toml
# ~/.cargo/config.toml (real path on this machine: /var/home/user/.cargo/config.toml)
[build]
build-dir = "{cargo-cache-home}/build/{workspace-path-hash}"
```

This is host configuration,
 not repository configuration.
It does not travel with a clone.
A fresh machine,
 a new contributor,
 or a container build needs the same two lines,
 or intermediates go back into `<package>/target/`.

The repository does ship two `.cargo/config.toml` files,
 and neither one sets `build.build-dir` or `build.target-dir`,
 so neither shadows the host value:

- `.cargo/config.toml` sets only `[env]`,
   namely `ZIG_GLOBAL_CACHE_DIR` and `SLINT_ENABLE_EXPERIMENTAL_FEATURES`.
- `package/music-player/desktop-app/.cargo/config.toml` sets only a `[target.<triple>]` `linker`
   (until 2026-10-14 it also set `rustflags` for the `gxhash` AES requirement documented in
   [`doc/troubleshooting/gxhash-aes-target-feature.md`](../troubleshooting/gxhash-aes-target-feature.md)).

Neither file is generated by file-enforcer,
 which touches Cargo manifests through `cargoProfileEnforcements` in `file-enforcer.config.ts`
 but has no rule for `.cargo/config.toml`.

## What Cargo splits

Cargo separates build output into two directories,
 per the [build cache reference][build-cache]:

- Final build artifacts go to the target-dir.
   These are outputs meant for end users:
   binaries for `bin` crates,
   `cargo doc` output,
   and `--timings` reports.
- Intermediate build artifacts go to the build-dir.
   These are internal to Cargo and rustc,
   and end users generally never touch them.

By default both point at `<workspace>/target`.
The setting above moves only the second category out of the repository tree.
`build.target-dir` is unset on this machine,
 so final artifacts still land in `<workspace>/target`.

That distinction is what keeps this repository's tasks working.
Everything under `<package>/target/debug/` and `<package>/target/release/` that a mise task or a
configuration file names is a final artifact,
 so it stays exactly where those paths expect it.

## How the template resolves here

The [configuration reference][config] documents three template variables for `build.build-dir`:

- `{workspace-root}` resolves to the root of the current workspace.
   Unused by this setting.
- `{cargo-cache-home}` resolves to `CARGO_HOME`.
   On this machine `CARGO_HOME=/home/user/.cargo`,
   so the prefix is `/home/user/.cargo/build`.
- `{workspace-path-hash}` resolves to a hash of the manifest path.
   It renders as two path segments,
   a two-character shard directory and a fourteen-character remainder,
   for example `cb/8094ff5b343153`.

So a resolved build dir on this machine looks like:

```txt
/home/user/.cargo/build/<2 hex>/<14 hex>/
```

The name `{cargo-cache-home}` invites the wrong guess.
It is not the `CARGO_CACHE_HOME` environment variable,
 which Cargo does not read for this key.
The environment override for this key is `CARGO_BUILD_BUILD_DIR`.

## Verified behavior on this machine

Measured 2026-09-19 with `cargo 1.100.0-nightly (3c0b53475 2026-09-04)` and
`rustc 1.100.0-nightly (0fc141305 2026-09-11)`.
Probes ran in throwaway crates under `~/temp/agent`,
 which were removed afterwards along with their build dirs,
 leaving `~/.cargo/build` absent as it was before.
No repository crate was built during the investigation;
 the repository-side checks below are read-only.

### The host value reaches repository packages

Run from inside a repository package,
 with `--show-origin` naming the file the value came from:

```sh
# /var/home/user/Monochromatic/package/rust-module/rust-linter-core
cargo config get build.build-dir --show-origin -Zunstable-options
# build.build-dir = "{cargo-cache-home}/build/{workspace-path-hash}" # /var/home/user/.cargo/config.toml

cargo config get build.target-dir --show-origin -Zunstable-options
# error: config value `build.target-dir` is not set
```

### Final artifacts stay local, intermediates do not

After one build of a throwaway `bin` crate,
 `<crate>/target/` held `CACHEDIR.TAG` and nothing else at its root,
 and `<crate>/target/debug/` held only final artifacts:
the executable,
 its `.d` dep-info file,
 `examples/`,
 and the two Cargo lock files,
 `.cargo-lock` and `.cargo-artifact-lock`.
It held no `deps/`,
 `build/`,
 `incremental/`,
 or `.fingerprint/`.
Those lived under the resolved build dir instead.

### Deleting `target/` does not force a recompile

`rm -rf target` followed by `cargo build` reported `Finished` in 0.00s and repopulated
`target/debug/`.
Cargo restores final artifacts from the build dir.
An empty or missing `target/` is therefore not evidence that a package was never built,
 and not evidence that a rebuild will be slow.

### Final artifacts are hardlinks into the build dir

```sh
stat --format='links=%h inode=%i %n' target/debug/bd-probe2
# links=2 inode=78846337 target/debug/bd-probe2

find ~/.cargo/build -inum 78846337
# /home/user/.cargo/build/e8/130f87be4e53c4/debug/build/bd-probe2/680339173169e6a8/out/bd_probe2
```

Both trees sit on the same Btrfs filesystem,
 `/var/home` on device 54,
 which is what makes the hardlink possible.
The `.d` dep-info files are not hardlinked and report `links=1`.

Because of the hardlink,
 adding a package's `target/` size to the build dir's size double-counts the final artifacts.
For physical disk use,
 apply the Btrfs-aware accounting that
[`doc/troubleshooting/pnpm-modules-cache.md`](../troubleshooting/pnpm-modules-cache.md) uses,
 namely `btrfs filesystem du -s`.

### `cargo clean` clears both sides

`cargo clean` in a throwaway crate reported `Removed 25 files, 8.7MiB total`,
 deleted that crate's build-dir hash directory,
 and deleted the local `target/`.
It left the two-character shard directory behind,
 empty.

### The hash keys on the workspace root, not the member

A throwaway workspace with members `a` and `b`,
 built from each member directory in turn,
 produced one build dir,
 `09/bf9fa3b5e5f937`,
 shared by both members.

### Path spelling does not change the hash

Building the same throwaway crate through its real path and through a symlink to it produced the same
build dir,
 `ca/964ece050f5927`,
 and the second run finished in 0.00s.
Cargo canonicalizes the manifest path before hashing.

This matters here because the repository is reachable both as `/home/user/Monochromatic` and as
`/var/home/user/Monochromatic`,
 a duality the root `.cargo/config.toml` already works around for `ZIG_GLOBAL_CACHE_DIR`.
Both spellings share one build dir.

Two genuinely different workspace paths do get different hashes:
 two sibling throwaway crates produced `90/064ca51498cbf1` and `e8/130f87be4e53c4`.

### `CARGO_CACHE_HOME` does not redirect it

With both `target/` and the crate's build-dir hash removed,
 `CARGO_CACHE_HOME=/tmp/cch-probe cargo build` recompiled into
`~/.cargo/build/e8/130f87be4e53c4` and never created `/tmp/cch-probe`.

### `CARGO_BUILD_BUILD_DIR` wins and is used verbatim

`CARGO_BUILD_BUILD_DIR=/tmp/bd-override cargo build` wrote
`/tmp/bd-override/.rustc_info.json` and `/tmp/bd-override/debug/`,
 and did not recreate `~/.cargo/build/e8`.
No template expansion is applied to a literal path given this way,
 so every workspace shares that one directory.
Useful for a one-off isolated build,
 wrong as a permanent setting.

## Consequences for this repository

### Every package is its own workspace

The repository has 19 Cargo manifests,
 counting every `Cargo.toml` outside `node_modules/` and outside any `target/`,
 and all 19 declare `[workspace]`.
There is no root `Cargo.toml`.
Each package therefore gets its own build dir,
 keyed by its own path,
 with no cache shared between packages.
That matches the pre-setting behavior,
 where each package had its own `target/`.

### Task and config paths that name `target/` keep working

These all point at final artifacts,
 which still land in `<package>/target/`:

- `cli-git.config.ts` names `./package/forbidden-strings/cli/target/release/forbidden-strings`.
- `file-enforcer.config.ts` names the same binary,
   plus the `.exe` spelling for Windows.
- `package/forbidden-strings/cli/mise.toml` names the same release binary.
- `package/cli/nested-wayland-session/mise.toml` runs `./target/release/monochromatic-nested-wayland-session`.
- `package/desktop-app/file-manager/mise.toml` runs `./target/debug/monochromatic-file-manager`.
- `package/desktop-app/file-manager-qt/mise.toml` runs `./target/debug/monochromatic-file-manager-qt`.
- `package/desktop-app/file-manager-gtk-sticky/mise.toml` runs
   `./target/debug/monochromatic-file-manager-gtk-sticky`.
- `package/desktop-app/file-manager-gtk-sticky/tests/wayland_boundary.rs` joins
   `target/release/monochromatic-file-manager-gtk-sticky` and a sibling package's
   `target/release/monochromatic-nested-wayland-session`.
- `package/wg/cli-quicker/src/privilege-context-data.unit.test.ts` and
   `package/wg/cli-quicker/src/application-exemption-command.unit.test.ts` use `target/release` fixture paths.

Two package-level `.gitignore` files pin `/target` for the same reason:
`package/music-player/truepeak-core/.gitignore` and `package/music-player/truepeak-core.bench/.gitignore`.
The root `.gitignore` already ignores `target/` globally.

### The existing `target/` trees predate the setting and are not shrunk by it

`package/rust-module/rust-linter-core/target/` still holds the old combined layout,
 with `build/`,
 `deps/`,
 and `incremental/` inside `target/debug/`.
Measured across the repository's `target/debug` and `target/release` directories,
 that is 20 GB,
 with the largest single trees being `package/cli/nested-wayland-session/target` at 6.3G,
 `package/forbidden-strings/cli.fuzz/target` at 5.8G,
 `package/linter/rust/target` at 4.4G,
 and `package/forbidden-strings/cli/target` at 3.1G.

Rebuilding a package puts its new intermediates in the host cache but leaves the stale in-repo copy
alone.
Reclaim that space once per package with `cargo clean`,
 or by deleting `<package>/target`.
The setting does not do it retroactively.

### `git clean -X` stops being a way to free Rust build space

Intermediates now live outside the repository,
 so `git clean -X`,
 worktree removal,
 and cli-git worktree copies neither carry nor reclaim them.
Both directions follow:
 worktree copies get cheaper because there is no multi-gigabyte `deps/` and `incremental/` inside the
tree,
 and repository-scoped cleanup no longer touches the bulk of Rust build output.

The git-safety rules in `AGENTS.md` that require inspecting ignored root artifacts before a cleanup
review still apply to `target/`,
 which remains present and ignored.
What changes is that `target/` no longer accounts for most of the bytes.

### Throwaway worktree builds outlive their worktree

A worktree at its own path gets its own build dir.
When the worktree is removed,
 its intermediates stay behind in `~/.cargo/build/`.
Worktrees created and discarded by cli-git accumulate this way.

### Nothing prunes `~/.cargo/build/` automatically

Cargo's global-cache auto-clean is controlled by `[cache] auto-clean-frequency`,
 defaulting to `"1 day"`,
 and the [configuration reference][config] states what it covers:
 registry indexes and source files downloaded from registries and git repositories.
The same note says support for tracking build artifacts is not yet implemented,
 tracked as [rust-lang/cargo#13136][cargo-13136].

So `~/.cargo/build/` grows until someone removes entries.
Two ways to reclaim space:

- `cargo clean` inside each package still built,
   which clears that package's build dir and its local `target/`.
- Delete `~/.cargo/build/<shard>/<hash>/` for workspace paths no longer built,
   such as removed worktrees.
   The shard directories are left behind empty and are harmless.

## Container builds do not inherit this setting

[`doc/decision/desktop-app-podman-build.md`](desktop-app-podman-build.md) runs Cargo on the host when
the native development libraries are present,
 and falls back to a Fedora podman container otherwise.
The fallback does not see this configuration:

- `package/music-player/desktop-app/Containerfile` and `package/desktop-app/terminal/Containerfile` both
   set `ENV CARGO_HOME=/cargo`.
- `package/music-player/desktop-app/mise.toml` mounts the package directory at `/work` and a named
   volume at `/cargo`,
   described in `package/music-player/desktop-app/Containerfile` as holding only the registry and git
   cache at run time.
   The host `~/.cargo/config.toml` is not among the mounts.
- The same `mise.toml` notes that podman does not forward host env into the container,
   and passes only a small explicit set of debug-info variables,
   so `CARGO_BUILD_BUILD_DIR` does not cross either.

Inside the container,
 `build.build-dir` therefore defaults to `build.target-dir`,
 and both resolve to `/work/target`,
 which is the bind-mounted package directory.
Container-built packages keep writing full intermediates into the repository tree.
Expect a mixed state on this machine:
 host-built packages with thin `target/` directories,
 container-built packages with full ones.

## Version floor

`build.build-dir` is documented in the 1.91.0 Cargo Book and absent from the 1.88.0 and 1.90.0 ones,
 checked by counting `build.build-dir` occurrences in each versioned
`cargo/reference/config.html`.
It is present in the current stable Cargo Book,
 so it is not nightly-gated.
Cargo on this machine is 1.100.0-nightly.

The template variables are documented alongside the key in the same reference,
 added by [rust-lang/cargo#15236][cargo-15236].

## The build-dir layout is internal

The [build cache reference][build-cache] states that the build-dir layout is internal to Cargo and
subject to change.
Nightly also carries `-Z build-dir-new-layout`,
 described in `cargo -Z help` as "Use the new build-dir filesystem layout",
 with the reorganization discussed in [rust-lang/cargo#15010][cargo-15010].

For diagnosis only,
 the layout observed on cargo 1.100.0-nightly with no `-Z` flags was:

```txt
# ~/.cargo/build/cb/8094ff5b343153
CACHEDIR.TAG
.rustc_info.json
debug/.cargo-build-lock
debug/incremental/<crate>-<hash>/s-<session>/*.o
debug/incremental/<crate>-<hash>/s-<session>/dep-graph.bin
debug/incremental/<crate>-<hash>/s-<session>/query-cache.bin
debug/incremental/<crate>-<hash>/s-<session>/work-products.bin
debug/build/<package>/<meta-hash>/out
debug/build/<package>/<meta-hash>/fingerprint
```

Do not write repository tooling that parses these paths.

## Finding a package's resolved build dir

Cargo prints no resolved build dir in normal output,
 and the investigation found no flag that reports one.
The trace log carries it in a `cache_location` span field:

```sh
# run from the package directory
CARGO_LOG=cargo::util::rustc=debug cargo build 2>&1 \
  | rg -o "$HOME/\.cargo/build/[0-9a-f]{2}/[0-9a-f]{14}" | sort -u
# /home/user/.cargo/build/cb/8094ff5b343153
```

That log target produced 14 lines for a throwaway crate build.
Widening to `CARGO_LOG=cargo=trace` also works and is much noisier.

For a one-off run where the location should be known in advance,
 set `CARGO_BUILD_BUILD_DIR` to an explicit path.
