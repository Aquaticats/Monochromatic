# Pi Advisor 0.0.1 with Pi 0.84.1: Kimi K3 reasoning exhausts the 16K response budget

## Symptom

A focused `advisor` call selected `hyper/kimi-k3`,
 returned several useful findings,
 then ended in the middle of:

```text
The container-mutability cause (`Array` vs `ReadonlyArray`) is not a declaration-ownership
```

The collapsed header said:

```text
advisor hyper/kimi-k3 278.5s hyper 665231/4126512 chars 166616 tokens full
```

`full` described the serialized input context,
 not the response.
 The persisted result recorded
`stopReason: "length"`,
 so the provider had exhausted its response budget.

## Root cause

### Advisor requested a 16,384-token response

At incident commit `3ef6fed29514fe2bad0728c9228f623f7d2516c7`,
`package/pi-plugin/advisor/src/constants.ts:38-41` defined the default:

```typescript
/**
 * Default maximum output tokens requested from the advisor model.
 */
export const DEFAULT_MAX_ADVISOR_OUTPUT_TOKENS = 16_384;
```

The user configuration selected the same value at incident time:

```json
{
  "timeoutMs": 600000,
  "maxAdvisorOutputTokens": 16384
}
```

`package/pi-plugin/advisor/src/advisor-client.ts:290-299` passes that value directly to Pi AI and also selects
Advisor's highest allowed reasoning level:

```typescript
const providerOptions: Omit<SimpleStreamOptions, 'signal' | 'timeoutMs'> = {
  maxTokens: options.config
    .maxAdvisorOutputTokens,
  ...(advisorReasoningLevel
    === undefined ? {} : { reasoning: advisorReasoningLevel, }),
```

The incident result reported:

```json
{
  "stopReason": "length",
  "usage": {
    "output": 16384,
    "reasoning": 15664
  }
}
```

Pi AI's usage contract says reasoning is already included in output.
`package/pi-plugin/advisor/node_modules/@earendil-works/pi-ai/dist/types.d.ts:253-264` states:

```typescript
export interface Usage {
    input: number;
    output: number;
    // ...
    /**
     * Reasoning/thinking tokens, when the provider reports them. This is a subset of
     * `output`: `output` already includes these tokens.
```

The OpenAI-compatible adapter applies that contract at
`package/pi-plugin/advisor/node_modules/@earendil-works/pi-ai/dist/api/openai-completions.js:1119-1126`:

```javascript
// OpenAI completion_tokens already includes reasoning_tokens.
const outputTokens = rawUsage.completion_tokens || 0;
const usage = {
    input,
    output: outputTokens,
    // ...
    reasoning: rawUsage.completion_tokens_details?.reasoning_tokens || 0,
```

The provider therefore spent 15,664 of 16,384 output tokens on reasoning.
 Only 720 reported output tokens were
outside reasoning.
 The returned visible text was 3,362 characters and ended mid-sentence.

### Pi preserved the provider's length signal

`package/pi-plugin/advisor/node_modules/@earendil-works/pi-ai/dist/api/openai-completions.js:1134-1142` maps the
provider finish reason without changing it:

```javascript
switch (reason) {
    case "stop":
    case "end":
        return { stopReason: "stop" };
    case "length":
        return { stopReason: "length" };
```

`package/pi-plugin/advisor/src/tool.ts:352-354` persists that state:

```typescript
truncated: advisorContext.truncated,
stopReason: response.stopReason,
usage: response.usage,
```

The truncation was therefore generated by the model response limit.
 It was not Pi's tool-output limit and not a
TUI display truncation.

### The header's `full` marker covers only input context

`package/pi-plugin/advisor/src/rendering-summary.ts:302-311` derives `full` solely from the serialized-context
flag:

```typescript
const truncated = details.truncated ? 'truncated' : 'full';
return [
  `${details.provider} ${details.contextChars}/${details.contextBudgetChars} chars`,
  `${details.estimatedInputTokens} tokens`,
  truncated,
]
```

The renderer does not show `details.stopReason`.
 A response can therefore say `full` while its generated answer
has stopped for `length`.

### A global 64K setting exceeds the selected model's advertised maximum

The installed model catalog reports:

```text
provider    model                  context  max-out  thinking  images
hyper       kimi-k3                1.0M     16K      yes       yes
synthetic   hf:moonshotai/Kimi-K3  524.3K   65.5K    yes       yes
```

Pi AI does not clamp an explicit configured value to `model.maxTokens`.
`package/pi-plugin/advisor/node_modules/@earendil-works/pi-ai/dist/api/simple-options.js:4-18` clamps only against
remaining context:

```javascript
export function clampMaxTokensToContext(model, context, maxTokens) {
    if (model.contextWindow <= 0)
        return Math.max(MIN_MAX_TOKENS, maxTokens);
    const available = model.contextWindow - estimateContextTokens(context).tokens - CONTEXT_SAFETY_TOKENS;
    return Math.min(maxTokens, Math.max(MIN_MAX_TOKENS, available));
}
// ...
maxTokens: clampMaxTokensToContext(model, context, options?.maxTokens ?? model.maxTokens),
```

Setting the global Advisor cap to 65,536 can therefore send a request above `hyper/kimi-k3`'s advertised
16K output maximum.
 Provider acceptance,
 rejection,
 or silent clamping has not been verified.

 Dividing review dimensions into separate calls
keeps each answer bounded without asking the selected model for an unsupported response size.

## What does not work

- Raising only `maxAdvisorOutputTokens` to 65,536 is not a sound fix for default selection.
  The selected `hyper/kimi-k3` model advertises 16K maximum output.
- The `full` header does not prove a complete response.
  It reports only whether serialized input context was truncated.
- A larger context window does not imply a larger output maximum.
  `hyper/kimi-k3` advertises a 1.0M context window and a separate 16K output maximum.
- The current plugin does not reserve a minimum visible answer after reasoning for OpenAI-compatible models.

## Resolution and remaining work

The Advisor default and user-level configuration now request 32,000 output tokens.
`package/pi-plugin/advisor/src/constants.ts:38-41` defines:

```typescript
/**
 * Default maximum output tokens requested from the advisor model.
 */
export const DEFAULT_MAX_ADVISOR_OUTPUT_TOKENS = 32_000;
```

`package/pi-plugin/advisor/src/output-eligibility.ts:34-55` filters each provider-specific model entry against
that configured requirement:

```typescript
export function filterAdvisorScopeByOutputCapacity(
  {
    scope,
    maxAdvisorOutputTokens,
  }: ForeignBorrowed<Readonly<{
    scope: ReadonlyDeep<EffectiveModelScope>;
    maxAdvisorOutputTokens: number;
  }>>,
): EffectiveModelScope {
  return {
    ...scope,
    entries: scope
      .entries
      .filter(function supportsConfiguredOutputCapacity(
        entry: ReadonlyDeep<ScopedAdvisorModel>,
      ): boolean {
        return entry
          .model
          .maxTokens
          >= maxAdvisorOutputTokens;
      },),
  };
}
```

Default selection requires a non-empty eligible scope.
Explicit selection resolves the requested model against authenticated scope first,
 then rejects it before provider dispatch when its endpoint advertises less than the configured value.
`package/pi-plugin/advisor/src/advisor-client.ts:219-226` repeats the assertion at the final provider boundary:

```typescript
assertAdvisorEndpointOutputCapacity({
  endpointSlug: modelSlug,
  advertisedOutputTokens: options.model
    .maxTokens,
  maxAdvisorOutputTokens: options.config
    .maxAdvisorOutputTokens,
},);
```

The main-model prompt and tool result details list eligible slugs,
 while `/advisor status` reports both raw scoped models and eligible Advisor models.

Targeted tests prove:

- a higher-cost endpoint below the requirement cannot win default selection;
- an explicit endpoint below the requirement is rejected;
- a model advertising exactly 32,000 remains eligible;
- an all-ineligible scope fails with endpoint capacities;
- provider dispatch count remains zero after default and explicit eligibility rejection;
- direct provider-client calls repeat the same capacity assertion;
- status and main-model guidance omit ineligible slugs from allowed candidates.

Focused continuations remain the verified recovery for a response that reaches `stopReason: "length"`.
The eligibility correction prevents configured output requests from exceeding model metadata,
 but it does not yet display response-length exhaustion in the collapsed header or automatically continue a
partial answer.

A 65,536-token cap would require every selected endpoint to advertise at least that value,
 followed by a real provider-boundary verification.
That 64K path was not executed during this diagnosis.

## Upstream filing decision

No `.out-of-scope/` entry matches this behavior.
Repository issue searches for `maxAdvisorOutputTokens`,
 `advisor output`,
 and `advisor reasoning` found no exact
local issue.
 Issues `#408` and `#412` cover attempt usage and no-text recovery,
 but neither acceptance list covers
a text-bearing `stopReason: "length"` response.

1. **Is it really upstream's fault?**
   No. Pi AI preserved the provider's usage and `length` finish reason.
    The local Advisor extension chose the
   16K cap,
    high reasoning,
    and misleading `full` rendering.
2. **Can upstream fix it?**
   Pi could add a model-cap clamp,
    but the complete user-facing correction belongs in the local Advisor policy
   and renderer.
3. **Are they supporting this use case?**
   Pi supports nested provider calls and custom tools.
    Its contracts expose the data Advisor needs.
4. **Would the repo welcome our contribution?**
   The local repository owns Advisor.
    No external Pi contribution is needed for the identified correction.
5. **Will they likely fix it?**
   Not applicable to external Pi because the deciding behavior is local.
6. **Have we prototyped a minimal upstream fix?**
   No upstream prototype is appropriate because constraint 1 fails.
    The automatic prototype gate does not
   trigger.

There is nothing additive to file in the external Pi tracker and no upstream issue draft to retain.
