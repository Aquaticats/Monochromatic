# Turso build timestamps change Android native artifact hashes

## Symptom

The frozen Android application source
`e02be6c8b8fe9efb41a7f8f1a0b311c17796588a`
produced different engine and Turso SDK library hashes in runs `qvsjm5hmdp` and `1jxc80q7q7`.
Both runs passed their native compilation commands.
The corrected second run also passed its APK layout and signature checks.
Artifact inequality alone did not identify a provider or cache defect.

## Root cause

The [retained section and source evidence][evidence] compares every section of the 64-bit libraries.
All compared `.text` sections match.
Each of the 6 differing engine/Turso libraries has exactly 4 different `.rodata` bytes,
inside an embedded build timestamp.
The ARM64 values are `2026-10-18 07:35:26` and `2026-10-18 07:56:35`;
the x86-64 values are `2026-10-18 07:36:33` and `2026-10-18 07:57:41`.
The `.symtab` and `.strtab` sections also differ,
with changed numeric LLVM symbol suffixes.
This comparison does not establish the cause of every symbol-table byte difference.

The locked `turso_core` `0.8.2` archive has SHA-256
`4fa832d4ab648bf139f1b18b29bef6d653b18fbd4a77b0e4846c57aaf28c215c`.
Its original `build.rs` has SHA-256
`390ef8d965fefcebd30143e681b7f273568f4c01f2fbbd9814cfe610bf3116cf`.
The cached source matches the original archive bytes;
this diagnosis does not rely on an unverified local registry edit.
The archive records upstream revision `5c168be5ef6a32ac966daf5983502a4f694b37ad`.

In that external crate's `build.rs:18`,
`env::var("SOURCE_DATE_EPOCH")` reads the optional timestamp seed.
The following `.ok()` and `epoch.parse::<i64>().ok()` discard missing or malformed input.

At `build.rs:66`,
the source selects the explicit seed,
then Git commit time,
then the current clock through `std::time::SystemTime::now()`.
The archived receipt retains the unchanged complete source,
including its original closures.

At `build.rs:79`,
that selected value becomes the generated `BUILT_TIME_SQLITE` constant.
An explicit seed also bypasses Git-derived revision metadata at `build.rs:26`.
The source already contains the reproducibility mechanism;
it does not require an upstream patch.

## Verification

The original build script and its locked `cfg_aliases` `0.2.2` input were compiled unchanged
inside a network-disabled container capped at 2 GiB and 2 CPUs.
The root filesystem was read-only,
only private output was writable,
and no repository write mount or ambient credential environment was passed.
The actual compiler was `rustc 1.97.1`.
That compiler is explicitly different from the Android producer's compiler;
this is a build-script behavior control.

- Two independent output directories with `SOURCE_DATE_EPOCH=0`
  generated byte-identical constants containing `1970-01-01 00:00:00`.
- Setting the seed to `946684800`
  changed the generated constant to `2000-01-01 00:00:00`.
  This positive control proves the probe can observe an input change.
- A malformed seed,
  with Git unavailable through the controlled `PATH`,
  generated the actual current UTC time.
- Each ELF section comparison also rejected a deliberate single-byte change in `.text`.

The complete outputs,
input hashes,
compiler image identity,
and command boundaries are retained in the evidence.
No complete Android rebuild with a fixed seed has been run in this profile.
Neither native-library bit reproducibility nor whole-APK reproducibility is established by this control.

## Verified workaround

For the build-script boundary,
pass a valid fixed `SOURCE_DATE_EPOCH` and retain its numeric value as a build and cache input.
Repeated identical seeds produce identical generated timestamp constants in the measured control.
Changing the seed changes those constants.

The tradeoff is that `sqlite_source_id()` metadata uses the selected timestamp and omits the Git hash.
A real CI policy must choose and record the seed before comparing cold and cached outputs.
The complete native and APK producer still needs a normalized rebuild comparison before any stronger claim.
Debug signing certificates and ZIP metadata are separate inputs.

## What does not work

- Treating identical application source and dependency locks as sufficient for byte identity
  while leaving an implicit build-clock input uncontrolled.
- Calling changed hashes a Depot regression without comparing their contents.
- Claiming that matching `.text` sections means the complete binaries match.
- Assuming the seed's presence is sufficient:
  the measured malformed value takes the clock fallback.
- Treating this unchanged build-script control as a complete Android reproducibility test.

## Upstream filing decision

[Turso pull request 6137][fix] already implements the relevant behavior
and was merged on 2026-04-01.
The installed locked source contains that fix.
The same upstream record also discusses hash-map ordering and Aegis CPU tuning,
which are distinct reproducibility surfaces;
they were not diagnosed as causes of this measured timestamp difference.
Issue search for `repo:tursodatabase/turso SOURCE_DATE_EPOCH`
returned 3 results with `incomplete_results: false` on 2026-10-18.
The `.out-of-scope/` inventory contains no Turso reproducibility exemption.

- Upstream fault:
  no current defect established;
  the supported seed was uncontrolled in the original experiment.
- Fixability:
  the needed upstream mechanism already exists.
- Supported use case:

- Contribution acceptance:

- Minimal prototype:
  no upstream source change is needed.
