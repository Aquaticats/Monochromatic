### Decided and built: queue tool calls, free only the read loop

Built as decided;
 `package/mcp/stdio/src/transport-queue.ts` holds the queue,
 and `serve()` in `transport.ts` enqueues rather than awaiting.
What follows is the reasoning it was built from.

`serve()` awaited each dispatch inline in the stdin read loop,
so a `run_in_vm` that takes 15 to 30 minutes blocked the loop:
the server could not even read `notifications/cancelled` while it ran.
The spec says a cancelled request's associated processing **SHOULD** cease.

The user chose the narrowest shape that fixes the actual complaint.
Only the read loop becomes concurrent.
Tool execution stays serialized behind a queue,
 so exactly one handler runs at a time,
 exactly as today.
`ToolHandler` keeps its current signature and no `AbortSignal` is introduced.

The payoff beyond merely reading cancellations:
 a cancelled request that is still queued and has not started yet is dropped before it ever runs.
That is strictly better than aborting one midway,
 because nothing has happened yet to leave half-done.

What this deliberately does not do,
 and why:

-   For a request already executing,
     it does not satisfy the spec's SHOULD that processing cease.
    That request runs to completion.
    Aborting `create_vm` or `update_templates` midway can strand a half-created VM
    or a half-built image,
     which is worse than letting it finish.
-   It gains no parallelism for genuinely independent calls.
    A `list_vms` issued during a long `create_vm` waits behind it.
    That cost was accepted deliberately in exchange for introducing no new interleaving.

Writes must still go through one queue,
 or frames interleave on stdout.

#### Narrowed from an earlier, broader shape

An earlier round recorded this as "concurrent dispatch,
 no `AbortSignal`",
 meaning handlers would run concurrently and only outbound writes would be serialized.
That shape carried an open worry:
 concurrent handlers let two VM mutations interleave where the transport had been
serializing them by accident rather than by design,
 which could open races in the mvm backend that did not exist before.

Serializing execution removes that worry rather than answering it.
There is no mvm race audit to perform before landing,
 because no two handlers ever run at once.
The transport's accidental serialization becomes deliberate.

### Decided and built: validate with valibot, deriving the advertised schema

Built;
 `package/mcp/stdio/src/tool-schema.ts` converts and validates,
 and all eight mvm tools declare their arguments in valibot.

#### The premise behind the original choice was wrong

The user first chose valibot over ajv on the basis that it was already a workspace
dependency,
 believing the package bundled its own JSON Schema adapter.
It does not:
 `valibot@1.4.2` ships a single `.` export with no JSON Schema symbol in its type surface,
 and conversion lives in the separate `@valibot/to-json-schema`,
 which was neither installed nor in the catalog.

The user was told this,
 re-opened the choice,
 and explicitly authorized adding `@valibot/to-json-schema` as a new dependency.
That makes `mcp-stdio` depend on something external for the first time,
 which was weighed against the alternative of a hand-written subset validator and accepted.

#### What measurement settled before any code was written

-   The converter emits `anyOf` for a union and valibot has no JSON Schema `not`,
     so `destroy_vm`'s `oneOf`/`not` cannot be reproduced literally.
    Strict branches restore the exclusivity instead:
     `additionalProperties: false` makes `{ name, all: true }` match neither branch.
-   A union converts to a bare `anyOf` with no root type,
     but revision 2026-07-28 states "Tool arguments are always JSON objects,
     so `type: "object"` is required at the root",
     so the root is restored after conversion.
-   The converter defaults to `draft-07`.
    The spec expects 2020-12,
     so conversion passes `target: 'draft-2020-12'`.
-   An unconvertible schema throws rather than degrading quietly.
    That is already the default;
     `errorMode: 'throw'` is passed anyway so a future default change cannot reintroduce
    silent lossiness.

#### Consequences worth knowing

Schemas are strict,
 so an argument no tool declares is now refused rather than ignored.
`backend` stays a free string rather than a picklist,
 so an unresolvable value still reaches `resolveBackendKind`,
 which names what it could not resolve.

`destroy_vm`'s refusal moved from an `isError` result to `-32602`,
 because the exclusivity rule is now expressible in the schema and a schema violation is
what `-32602` means.
The wording a caller reads is preserved through the union's own message,
 since a bare union mismatch would report a type error rather than state the rule.
The handler guard this handover previously insisted on keeping is therefore gone,
 replaced by a check that runs strictly earlier,
 before dispatch rather than inside it.

Validation is a gate only.
Handlers still receive the arguments as sent,
 because valibot object schemas drop undeclared keys and passing the parsed value would
quietly change what every handler sees.

## Do not verify with `claude mcp list`

It sends `initialize` as its first and only message,
 never `server/discover`,
 so it reports this server as failed no matter how healthy the server is.
Measured by tapping a disposable registration:
 one `initialize` in,
 one `-32601` out.

Probing is gated remotely by `tengu_mcp_protocol_negotiation_stdio`,
 which defaults to off,
 so this is not stable over time:
 the same setup connected earlier the same day and failed later with no local change.
While the gate is off this server is unreachable from Claude Code entirely,
 not merely mis-reported by the CLI.
Verify by driving the built binary over stdio.

Source trace:
 `doc/troubleshooting/claude-code-mcp-protocol-negotiation.md`.

The decision stands after being re-put with that cost on the table:
 stay modern-only and accept the unreachability.
Do not add a legacy fallback to make the CLI go green;
 that was considered and declined.

## How to verify anything here

Both packages build,
 lint,
 type-check,
 and test through mise:

```sh
mise run //package/mcp/stdio:lint
mise run //package/mcp/stdio:buildAndTest
mise run //package/mcp/mvm:lint
mise run //package/mcp/mvm:buildAndTest
```

`buildAndTest` is required rather than `test:unit` alone:
both suites import the built artifact,
 so a source-only run tests stale output.

End-user verification goes through the client,
 not the test suite:

```sh
mise run //package/mcp/mvm:build
claude mcp get mvm
```

To see the actual wire exchange,
 register a tap that pipes stdio through to the real bin
while appending both directions to a log,
 then health-check the tap.
That is how the modern-path negotiation was confirmed;
the recipe is in the planning doc's verification section.

## Gotchas worth knowing before editing

-   **Read the full lint output,
     never a grep of its summary lines.**
    The rules in this repo carry ranked remediation instructions in the message body.
    Grepping cost a wrong fix once already:
     `no-nullish-union` names an empty object outright
    as a banned stand-in for absent,
     which a summary-line grep hides.
-   **Tests must import built output,
     not package source.**
    `require-eventual-artifact` enforces it.
    A behavior only reachable through a source symbol gets tested over stdio through the bin instead.
-   **Never let a `destroy_vm` test reach a real backend.**
    Every such case pins `backend` to a kind nothing resolves,
    so even an accepted call cannot destroy anything.
-   **`~/.claude.json` is rewritten by concurrent sessions.**
    Change MCP registrations with `claude mcp add`/`remove`,
     never by hand-editing the file.
-   **The client caches server era per process.**
    After changing protocol behavior,
     rebuild before re-running `claude mcp get`,
    or the health check exercises the previous binary.
