First: four tiny words

Secret management sounds scary because people use big words. The cave version has only four pieces.

💎

Secret

The shiny thing we must hide. Example: API key, password, token, private key.

📦

Locked box

Encryption turns secret into locked box. People can see box. People cannot eat shiny thing inside.

🗝️

Two keys

Modern locks come as a pair. The locking key (public) only seals boxes; living in Git is fine. The opening key (private) unseals them; never in Git.

🔥

Consumer

The thing that needs the shiny to do work. Maybe a human running a command. Maybe a robot deploying code. Who the consumer is decides where the opening key has to live.

Why "locked box in Git" is even a thing

The trick that makes the whole story work is asymmetric crypto. The locking key and the opening key are different. The locking key can lock, but cannot open. The opening key can open, but is never asked to lock.

🔓 Locking key (public)

Anyone can have it. Anyone can drop a secret in and click the lid shut. Sitting in Git, on the wiki, on a sticker: all fine.

🗝️ Opening key (private)

Only the consumer holds it. Not on the laptop unless the laptop is the consumer. Never in Git. Treat exactly like the secret itself.

Cave version: the basket has a clamp anyone can press shut. Only the chief's special bone slides it open again. Tribe carries locked baskets around freely. The chief guards the bone.

Why this matters: if locking and opening used the same key, putting a locked box in Git would be pointless (the key would have to live somewhere to do the locking). Asymmetric crypto is what lets Git carry locked boxes safely.

When would anyone put encrypted secrets in Git?

Almost never for normal local dev. It makes sense when Git is not just code storage. It makes sense when Git is the delivery wagon that feeds the machine.

Kubernetes GitOps: the robot only reads Git

Baby version: robot watches picture book. Put locked snack in picture book. Robot has key at home. Robot opens snack only at home.

Cave version: tribe paints cave wall. Fire spirit copies wall. Secret meat on wall is bad. Locked meat drawing is okay if only fire spirit has bone key.

When good: a controller like Flux pulls Git and can decrypt inside the cluster.

When bad: a human is just running local commands. Use a local secret store instead.

Bad patterns: mammoth steals shiny thing

These are the mistakes that make encrypted secrets pointless.

Bad: box and key in same cave

Committing .env.enc and .env.key is like locking meat in a box and taping key to the box.

Bad mammoth result: anyone with Git opens it.

Good: Git has box, machine has key

Git stores encrypted text. The private key lives outside Git, on the machine or in a platform secret store.

Good tribe result: Git alone is not enough.

Bad: decrypt forever into repo

Running sops -d .env.sops > .env and leaving it there recreates the original problem.

Bad mammoth result: plaintext sleeps on cave floor.

Good: inject at run time

Use a wrapper that reads secret, starts command, and does not leave plaintext files behind.

Good tribe result: secret appears only when fire needs it.

Bad: base64 is not encryption

Wrapping a secret in btoa() or base64 -e only changes the look. Anyone can reverse it in a browser tab in two seconds.

Bad mammoth result: shiny thing was never locked. Just hidden under a leaf.

Good: real encryption with a real key pair

Use age, GPG, or SOPS. The output looks like noise. Reversing it requires the private opening key.

Good tribe result: mammoth chews on the basket. Mammoth gets nothing.

Bad: commit .env "just for a minute"

Git remembers. One commit with plaintext stays in history even after a follow-up commit removes it. The shiny thing is now in every clone forever.

Bad mammoth result: every copy of the cave wall carries the smear, even after you scrubbed the current one.

Good: .gitignore before the first add

Add the file pattern to .gitignore before any secret value is written. If a plaintext secret ever was pushed, rotate it and treat it as compromised; rewriting history rarely catches every clone.

Good tribe result: the wall never sees the meat in the first place.

Bad: rotate the key, leave old boxes alone

If the opening key was leaked, generating a fresh one only protects future commits. Old encrypted files in Git history still open with the old, stolen key.

Bad mammoth result: new bone, same old locked drawings the thief can still open.

Good: rotate, re-encrypt history, rotate the secrets too

Generate a new key pair. Re-encrypt every existing secret file with the new locking key. Then rotate the underlying secret values too. They were exposed the moment the key leaked.

Good tribe result: fresh bone, fresh drawings, fresh meat. Old thief holds nothing useful.

The hardest truth: locked is not forever

Committed encrypted secrets stay safe only while the opening key stays secret. The day that key leaks, every committed encrypted file back to the first commit opens up. Live secret services can rotate the value and make old captured ciphertext useless. Git history cannot rewrite itself in every clone.

Cave version: if the chief's bone is ever stolen, every old wall-drawing that bone could open is now open. The wall cannot be re-painted in every other tribe's cave.

What this means in practice: committed encrypted secrets fit when (a) the consumer needs the secret to arrive through Git, and (b) the value can be rotated soon if the key is ever lost. For short-lived developer tokens with no Git consumer, use a live store and skip Git entirely.

Tool map: which cave tool does what?

Tools are not moral. Each tool is good when used for its job.

🧰 gopass / pass local store

Job: keep secrets outside the repo and fetch them when commands run.

Use when: developer API keys, OpenTofu provider env vars, local tokens.

Cave words: personal pouch with lock.

gopass vs pass: gopass is a Go-based fork of pass with friendlier multi-recipient support, team workflows, and an age backend. pass is fine for solo bash setups; pick gopass for teams.

📦 SOPS + age locked files

Job: put encrypted secret files in Git when Git must deliver them.

Use when: Flux, NixOS secrets, GitOps, offline recovery bundles.

Cave words: locked box on delivery wagon.

🏠 sops-nix / agenix NixOS

Job: declarative secrets for NixOS hosts; activation decrypts to runtime-only paths (/run/secrets).

Use when: the whole machine is described by a Nix flake and Git is the source of truth for it.

Cave words: recipe book includes a sealed envelope; the kitchen opens it during cooking.

sops-nix vs agenix: sops-nix wraps the same SOPS files you might use elsewhere; agenix is age-only and a bit leaner. Pick by whichever your other tooling already speaks.

🔐 git-crypt transparent

Job: transparently encrypt selected files on commit and decrypt them on checkout (GPG-based).

Use when: developers and CI bots with the right key see plaintext locally; remote storage and other clones see only ciphertext. Smaller teams, single repo.

Cave words: cave front door has a curtain; tribe members with the right necklace see meat, strangers see only the curtain pattern.

Watch out: once decrypted in a working copy, the secret lives on disk as plaintext. Same forward-secrecy caveats as SOPS.

🏗️ OpenTofu encryption state

Job: protect state and plan files at rest.

Use when: terraform.tfstate and saved plans may hold sensitive values.

Cave words: official lock for map of village.

☁️ Platform secrets CI/deploy

Job: give secrets to GitHub Actions or Coolify without putting them in Git.

Use when: CI jobs or deployed apps need env vars.

Cave words: gatekeeper hands key to worker.

🏛️ OpenBao / Vault live service

Job: a running service that issues, rotates, and audits secrets via API; the consumer asks for a fresh value each time.

Use when: larger teams, dynamic per-environment credentials, audit logging, fast rotation across many consumers.

Cave words: dedicated chief at the gate who hands out fresh bones on demand and writes down who got which one.

Skip when: a small repo with a handful of API keys. The running chief is more work than the secrets.

What this means for Monochromatic

This repo is mostly command-driven and env-var-driven. It is not currently a GitOps repo. So the boring answer is the good answer.

Use now

  • gopass with age: local API keys and provider tokens.
  • mise TypeScript wrappers: inject env vars for commands.
  • OpenTofu state encryption: protect state/plan files.
  • GitHub/Coolify secrets: keep platform secrets where platform runs.

Do not start with

  • SOPS as repo-wide secret storage: no current Git consumer needs it.
  • OpenBao: too much cave machinery for local env keys.
  • Plain .env.local as default: easy, but plaintext on disk.
  • Secret tfvars files: provider env vars are cleaner.

What does a mise wrapper actually look like?

A small TypeScript file in package/<pkg>/src/ reads the secret from gopass and starts the real command with the env var set. Nothing lands on disk as plaintext. 

// package/<pkg>/src/mise.deploy.ts
import { $ } from 'bun';

const apiKey = (await $`gopass show -o providers/openrouter/api_key`.text()).trim();

await $`./scripts/deploy.ts`.env({
  ...process.env,
  OPENROUTER_API_KEY: apiKey,
});

The matching mise.toml task runs bun src/mise.deploy.ts. The secret value only lives in process memory for the lifetime of the spawned command.

Small glossary

What is plaintext?

Text people can read directly. API_KEY=abc123 is plaintext. Cave wall has shiny thing written on it.

What is ciphertext?

Encrypted text. People can copy it, but cannot understand it without key. Cave wall has locked-box drawing.

What is GitOps?

A robot watches Git and makes real machines match Git. If Git says three fires, robot makes three fires. If Git says locked secret, robot opens it only where it runs.

What is state?

OpenTofu state is the map of what infrastructure exists. It may contain secret-looking things. Protect it with OpenTofu state encryption, not random cave blanket.

What is rotation?

Replacing a secret or a key with a fresh one. For values: ask the upstream service to issue a new token, then update consumers. For opening keys: generate a new key pair, re-encrypt every existing secret file with the new locking key, and revoke the old key on consumers. Rotation is what limits the blast radius when something leaks.

What is forward secrecy here?

The property that old ciphertext stays unreadable even after a future key compromise. Committed SOPS files do not have it: a future leak of the opening key opens every old commit. Live secret services can rotate values so old captures become useless. Plan accordingly.

What is asymmetric encryption?

Encryption that uses a key pair instead of one shared key. The locking key (public) can seal a box. The opening key (private) can unseal it. They are mathematically linked at generation time but cannot be derived from each other. This is what makes "locked box in Git" possible without putting any usable key in Git.

One-sentence cave law: if Git is just a notebook, do not put secret boxes there; if Git is the delivery cart that a robot consumes, locked boxes in Git can make sense.
