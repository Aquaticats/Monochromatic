Selected Search interaction (D63 to D68)

Opening Search requests query edit focus and a keyboard (D63). The visible Back arrow returns directly to the player, including while the keyboard is shown (D64). Clear erases the query but keeps Search and its existing edit-focus/keyboard state (D65). Opening Search again from the player starts a fresh empty query (D66); if a future design instead restores query text, it would begin its results at the top (conditional D67). With the same query after hiding and refocusing the keyboard, the intended result row should remain visible in the resized viewport, not merely retain a raw scroll offset (D68). These are selected interaction goals, not demonstrated by the keyboard-closed captures or the archived logic-only comparison. The D56 final-row extra swipe is an observed limitation, not accepted behavior; native restoration across keyboards still needs implementation-boundary verification. System Back may first be handled by the IME and is not promised to be identical to the visible Back arrow. The left browser context and full playback deck remain intact. Historical interaction alternatives are archived, not active choices.

Selected Search status meanings (D69 to D71)

An empty query shows an invitation to search, not a failed lookup. A “no results” message requires a completed evaluation of the current query and source; an empty track list or partial read cannot prove it (D69). The existing unqueried prompt and the no-match treatment naming the entered query remain the visual directions (D70). The old forced “Library unavailable” fixture and its automatic-recovery promise are not selected: only a known Search-source failure can show a cause-specific unavailable message with a genuinely owned recovery action (D71). The keyboard-closed native status gallery retains those historical fixture strings for evidence, not as a selected recovery UI. No search engine, live source-health signal or error action is present in these screenshots.

Selected result action (D72 to D74)

A folder result returns to the player with that folder selected, changing the queue page scope without starting another track (D72). A directly named track result starts a different track, or toggles play/pause if it is already current, as existing player rows do (D73). After either successful track action, Search returns to the player (D74), so the ordinary folder view is visible and a later Search opens empty under D66. A stale result must not start a substitute or pretend playback succeeded; D9's missing-item bar is a precedent to verify later. Neither the static result rows nor the older captions “opens this folder” and “reveals track” have a working tap handler; actual activation, row scrolling and TalkBack behavior remain unverified. The historical interaction comparison is not an active choice.

Adopted accessibility goals (D75 to D80)

Search opens with query accessibility focus (D75), separately from D63's edit-focus/keyboard request. Back stays reachable by reverse navigation. Keep Back/query/Clear and results or current status together in reading order; then traverse the retained inner folder region and full deck without interleaving the alphabet rail (D76). Search is not a focus trap: named retained regions must remain reachable without stepping through every hit.

Each result is one action with its own name once, kind, disambiguating parent context and the actual Open/Play/Pause meaning (D77). Announce meaningful current-query result/status changes without stealing focus or announcing every key; never turn a partial read into completed no match (D78). Visible Back restores the invoking player control. Successful activation focuses the revealed folder or track context; failed activation stays in Search with a truthful diagnostic (D79). Same-query updates preserve surviving item identity, with explicit fallback when a result or Clear disappears (D80).

Design goals, not verified native behavior. The bounded inner baseline at 200% text and keyboard closed interleaved the left alphabet rail and separated result title/detail stops. Cover swipe delivery lacked a positive control. The inspected witnesses are documented at package/music-player/design/evidence/search-talkback-native-baseline.md. The user accepted these reviewed goals as good enough; the chat correction path remains available. Native entry, rows, announcements, return focus and fold continuity still need implementation-boundary verification; exact source recovery remains deferred. No new keyboard experiment or production Search change was made.
