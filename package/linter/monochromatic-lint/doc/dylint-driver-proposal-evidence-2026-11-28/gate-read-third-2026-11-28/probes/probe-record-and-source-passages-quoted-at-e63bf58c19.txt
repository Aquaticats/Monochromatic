## package/linter/monochromatic-lint-closure/README.md lines 183 to 215
183	### Toolchain
184	
185	The package uses the repository's shared floating nightly,
186	declared in the root `mise.toml` with the `rustc-dev` component
187	(a Dylint library links rustc's own crates)
188	and the tools `cargo-dylint` and `dylint-link` (the owner approved this on 2026-10-18).
189	`mise install` provisions all three;
190	nothing else is needed,
191	and the package has no `rust-toolchain.toml` and no toolchain override of its own.
192	The exact nightly is whatever `mise.lock` resolves for the `rust` entry.
193	Dylint builds a library and every package it lints with that nightly,
194	and `cargo dylint` caches its driver in `~/.dylint_drivers` (the optional `DYLINT_DRIVER_PATH` moves it).
195	
196	A floating-nightly upgrade can break the lint source:
197	rustc's internal API moves between nightlies,
198	so after `mise.lock` moves the nightly,
199	build the library and run the tests before relying on the lint,
200	and fix the source if the compiler's API changed.
201	The `dylint_linting` and `dylint_testing` crates and the two tools must stay on the same Dylint release.
202	
203	#### What a nightly bump has needed so far
204	
205	Measured on `nightly-2026-11-16`:
206	
207	- No Dylint release had to change.
208	  Dylint publishes when a nightly breaks its crates;
209	  the newest `dylint_linting`,
210	  6.4.0 (published 2026-11-10),
211	  compiles against this nightly,
212	  its own lint template pins `nightly-2026-08-20`,
213	  and the crates and tools were already on 6.4.0.
214	  A compile failure after a bump is therefore first a question about this crate's own source,
215	  not about the version floor.
