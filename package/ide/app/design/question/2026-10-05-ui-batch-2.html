IDE UI batch 2: five questions

Purpose: five small UI decisions about the read-only Slint IDE (package/ide/app) are open. Each option below was built for real on a throwaway prototype branch and captured in the running app, in the nested compositor, in the dark and the light scheme. The first four questions were asked for; the fifth, selected-row ink, was added so that this page shows it too.

What to inspect: for each question, the crops under one state heading show the same moment in every option, at the same scale, cut from the same rectangle of a 1100 by 660 window. Options sit side by side where the browser window fits their crops at full size and stack otherwise; a crop shrinks only when the window is narrower than the crop. Select a crop to open its full frame. Option A is always what main draws today; a green "Current main" tag and a doubled green border mark it, and a blue "Ranked first" tag marks the option this page ranks first.

Which main: option A was built from main at a630b237b. While this page was made, main gained language navigation (a hover popup and a references list). The files that draw everything shown here (ui/divider.slint, ui/tree.slint, ui/find.slint, ui/search.slint) are identical on main at 2c64f0229; ui/app.slint changed there only for language navigation and an outside-project label, neither of which appears in these scenes.

Scale: the frames were captured at scale factor 1, so on a display scaled 2 or 3 times they look softer than the running application would; sizes and positions are true.

How to respond: answers are collected in the chat, not on this page. For each question, reply with an option letter, or a letter plus a change. The ranking is a recommendation with reasons, not a decision.

1. Divider gap

How should the sidebar divider spend its 48 px minimum grab width?

On main the divider is a 1 px line centered in its own 48 px layout cell (ui/divider.slint, ui/app.slint), so its grab area overlaps no tree row and no source text. The cost is about 47 px of empty column that reads as padding. The repo rule for custom interactive elements asks for an explicit 48 px minimum and no reliance on a touch area that overlaps neighbors; option B breaks that rule and would need your exception. Options C and D are additions: they keep the rule and change only how the same cell looks.

Options

A: Keep the 48 px cell, line centered (current main)

The current main build.

Pros

  • Meets the 48 px target rule with no exception: every pixel of the grab area belongs to the divider, so tree rows and the source keep all of their own pointer area.
  • The hit area is symmetric around the visible line: 24 px on the tree side, 23 px on the source side.

Cons

  • About 47 px of column looks like padding and carries no visible meaning until the pointer finds it.
  • The source column is 47 px narrower than with option B.

Build: main a630b237b.

B: 1 px cell with a 48 px grab area overlapping tree and source

The layout cell is only the line. The divider is split in two: its keyboard half stays in the 1 px cell, so Tab order is unchanged; its pointer half is a 48 px overlay centered on the line and declared after the layout, so it sits above the tree and the source and takes the pointer first.

Pros

  • Densest: the source column gains 47 px and the tree meets the line directly.
  • Common desktop practice: the VS Code sash is 4 px centered on the boundary and laid over both views (src/vs/base/browser/ui/sash/sash.ts, globalSize = 4 and left - size / 2), and GTK 4 GtkPaned grows a thin handle's input area by 6 px on every side (gtk/gtkpaned.c, HANDLE_EXTRA_SIZE).

Cons

  • Needs your exception to the rule against touch areas that overlap neighbors.
  • The last 24 px of every tree row stop being the row: hover and click there resize instead (the pointer-on-a-tree-row frame shows README.md losing its hover). Long names elide 15 px before the line, so the grab also covers about 9 px of label ink.
  • Keyboard focus draws its boundary across tree rows and the source gutter. By the gutter's geometry (44 px, right-aligned, about 9 px per digit), three-digit line numbers would begin about 6 px inside the grab area; line 100 is not in these frames.

Build: commit 5de82698c on prototype/ide-ui-variants.

C: 48 px cell with the line on its tree-side edge

Added variant: same cell and hit area as A; only the line moves to the cell's left edge, so the tree looks bounded tightly and the empty space reads as the source column's left margin. It tests whether position alone fixes "reads as padding".

Pros

  • Meets the 48 px rule with no exception.
  • The tree region ends at the line, so the selected row's fill and the line meet cleanly.

Cons

  • The grab area extends 47 px to the right of the visible line and none to its left, so a press 40 px from the line still resizes it.
  • Line numbers start 75 px right of the line, against 51 px in A, so the empty space looks wider.
  • The focus boundary's left edge and the heavy line coincide, so focus reads mostly as the right boundary.

Build: commit 106ab1ea4 on prototype/ide-ui-variants.

D: 48 px cell with a Material 3 style drag handle

Added variant: same cell and hit area as A, plus a rounded handle centered in the cell, so the gap reads as a control rather than padding. Sizes follow the Material 3 drag handle tokens in androidx (DragHandleTokens.kt: 4 by 48 dp idle in a 24 dp container, 12 by 52 dp pressed or dragged, fully rounded). Hover makes it 8 px wide and brighter; focus adds the cell boundary at full ink.

Pros

  • Meets the 48 px rule with no exception.
  • Explains the gap: the handle says "drag here" without hover, and each state changes two channels (width and ink).

Cons

  • Still spends 47 px of width.
  • One more drawn element; Material styling inside an otherwise fluent-styled desktop app.
  • The handle sits at the window's mid height, so with a short tree it floats beside unrelated source lines.

Build: commit 6b74bf6c4 on prototype/ide-ui-variants.

Ranking

Ranking: D > A > C > B

  • D over A: same rule-compliant hit area, but D addresses the stated problem, the gap reading as padding, by making the gap visibly a control.
  • A over C: A's hit area is centered on what you see; C puts the whole grab area to one side of the line and widens the empty space before the source.
  • C over B: C keeps the 48 px rule and every tree-row pixel; B needs an exception and takes 24 px of every row.

2. Divider as a keyboard Tab stop

Should the sidebar divider be a Tab stop with arrow-key resizing?

On main, Tab goes tree, divider, source; Left and Right resize by 16 px and Home and End jump to the bounds; the focused divider shows a 3 px line plus a boundary around its cell. Only option A has a divider state of its own, so the frames show the same key presses in every option: Tab from the source to the tree, one more Tab, then Shift+Tab back to the tree and Alt+Shift+Right three times.

Same scene, every option

Tree focused

One Tab from the source, which has focus at start. The same in every option.

One more Tab

A stops on the divider; B and C go straight to the source.

Shift+Tab to the tree, then Alt+Shift+Right three times

Shows whether a key resizes the sidebar while the tree has focus.

Options

A: Keep the divider as a Tab stop (current main)

The current main build.

Pros

  • Keyboard resizing is discoverable by Tab alone and shows a focus state while active.
  • Follows the WAI-ARIA window splitter pattern: a focusable separator moved with the arrow keys, with optional Home and End.

Cons

  • Every Tab cycle passes one extra stop between tree and source that does nothing else.

Build: main a630b237b.

B: Not a Tab stop; Alt+Shift+Left and Alt+Shift+Right resize from anywhere

The divider's key scope no longer takes Tab focus. The window's key capture resizes the sidebar by 16 px on Alt+Shift+Left or Alt+Shift+Right whatever has focus, except while the search overlay is open; the frames exercise it from the tree.

Pros

  • Tab goes straight from tree to source.
  • Keyboard resizing still exists, from wherever focus is.

Cons

  • Nothing on screen teaches the shortcut and nothing marks resizing while it happens; it needs documentation.
  • Precedent uses other keys: the IntelliJ IDEA tool-window shortcuts list Ctrl+Alt+Shift+Left and Right as Stretch to Left and Right, and GTK GtkPaned binds F8 to focus its handle for the arrow keys (gtk/gtkpaned.c, cycle-handle-focus). The JetBrains keys were measured as taken on this host: its GNOME window-manager settings (org.gnome.desktop.wm.keybindings, move-to-workspace-left and -right) include them, and its KDE global shortcuts bind them to JuK seek, so this build drops Ctrl. Alt+Shift+arrows may still collide on other desktops.

Build: commit 4133d984b on prototype/ide-ui-variants.

C: Not a Tab stop; no keyboard resizing

The divider's key scope no longer takes focus at all, so its arrow keys are unreachable.

Pros

  • Simplest: Tab goes straight from tree to source, and there is nothing hidden to document.
  • Assistive technology still has the slider's increment, decrement, and set-value actions.

Cons

  • A keyboard-only user cannot resize the sidebar.

Build: commit b1cc52b81 on prototype/ide-ui-variants.

Ranking

Ranking: A > B > C

  • A over B: A's cost is one Tab stop; B removes it but hides the feature behind an undiscoverable chord that the measured desktops already contest in its JetBrains form.
  • B over C: B keeps keyboard resizing for people who learn the chord; C removes it outright.

3. Clear icon in the text inputs

Should the find input and the combined-search input keep the toolkit's clear (x) icon?

Both inputs use the fluent LineEdit from Slint 1.18.1 (ui/find.slint, ui/search.slint). It shows a clear icon while it has focus and text; the icon is a 16 px wide image whose own area clears the text (widgets/fluent/lineedit.slint in the Slint compiler crate), so its pointer target is 16 px wide inside these 48 px tall inputs. Option B replaces both inputs with a custom input built on TextInput that copies the fluent look.

Options

A: Keep the toolkit clear icon (current main)

The current main build.

Pros

  • No custom code: the toolkit keeps owning text editing, the caret, selection, the right-click menu, and input methods.
  • One click clears the text.

Cons

  • Its pointer target is 16 px wide, below the 48 px minimum this repo asks of interactive elements (the rule is written for custom elements; this one is the toolkit's).
  • An x in the find bar reads like "close the find bar". If question 4 picks buttons, the bar shows two x marks side by side with different meanings (see the find bar buttons frames).

Build: main a630b237b.

B: Remove the icon with a custom input on `TextInput`

A new ui/plain-input.slint copies the fluent LineEdit values for both schemes (12 px side padding, 4 px corners, the gradient border, the focused fill, the 2 px accent underline, placeholder ink, selection colors, and caret-follow scrolling) and is used by both inputs.

Pros

  • No sub-48 px target inside the inputs and no second x in the find bar.
  • Measured to look the same: inside each crop, B differs from A only by the icon glyph.

Cons

  • A custom input to maintain: it will not follow future toolkit changes to LineEdit.
  • The prototype does not rebuild the toolkit's right-click menu (undo, redo, cut, copy, paste, select all); a real B must, and input-method preedit needs a check.
  • Clearing takes Ctrl+A then Backspace instead of one click.

Build: commit a79ac704f on prototype/ide-ui-variants.

Ranking

Ranking: B > A

  • B over A: B removes a 16 px target and an x that competes with "close", at the same look; A wins only if keeping toolkit-owned editing matters more than both. If question 4 stays keyboard-only, the competing x is gone and the gap between B and A narrows.

4. Find bar buttons

Should the find bar have previous, next, and close buttons?

On main the find bar has no buttons: Enter and Shift+Enter move between matches and Escape closes it (ui/find.slint). Option B adds three 48 px buttons where browser find bars put them, after the match count. Both options here keep the toolkit clear icon from main, so question 3 is not mixed in.

Ctrl+F from the source, then type Latin. Status 1/200, caret in the input.

Pointer on next

Option B only: the pointer rests on the next button.

After clicking next

Option B only: one seat click on next. Enter does the same in both options.

No matches

Ctrl+A, then type zzz.

Options

A: No buttons: Enter, Shift+Enter, Escape (current main)

The current main build.

Pros

  • Nothing to add; the input keeps the full bar width.
  • No extra pointer targets competing with the clear icon.

Cons

  • Pointer users get no visible way to step through matches or close the bar; the keys are learned, not seen.

Build: main a630b237b.

B: Previous, next, and close buttons after the count

Three pointer buttons drawn with vector glyphs (system fonts are isolated in this app). They never take keyboard focus, so a click leaves the caret in the input; Enter, Shift+Enter, and Escape keep working. States use two channels each: idle is a faint boundary; hover adds a fill and a full-ink boundary; press adds a stronger fill and a 2 px boundary; disabled drops the boundary and dims the glyph. Previous and next disable while there is no text, no match, or a refused query.

Pros

  • Visible, pointer-reachable stepping and closing, in the order of the browser find bar that editord's Ctrl+F opens: Chromium 149 (chrome/browser/ui/views/find_bar_view.cc, tag 149.0.7827.54) builds text field, match count, separator, previous (arrow up), next (arrow down), close. This prototype omits the separator.
  • The disabled pair repeats "No matches" without relying on the text alone.

Cons

  • The input loses 164 px (728 to 564 px at this window size).
  • With the clear icon kept, the bar shows two x marks: clear inside the input and close at the end.
  • Not Tab stops in this prototype: keyboard users rely on the keys. Chromium's buttons can take focus (the same file checks their focus), so making these Tab stops is a further choice.
  • The prototype's glyphs are 8 px marks inside 48 px buttons; a real build would size them to the toolkit icons.

Build: commit d8d28717a on prototype/ide-ui-variants.

Ranking

Ranking: B > A

  • B over A: B makes stepping and closing visible to pointer users at the cost of 164 px of input width, which a find query rarely needs; pairing B with removing the clear icon (question 3, option B) avoids the double x.

5. Selected-row ink

Should selected rows draw white text on the blue selection fill in both schemes?

The selected row in the file tree (ui/tree.slint) and in the combined-search list (ui/search.slint) takes its text color from the toolkit palette's selection ink, which is black in the dark scheme and white in the light scheme, over the same blue fill (#0078D4). The source view already switched its selected text to white in both schemes; doc/handover/slint-ide-0x.md records that change with its contrast figures. The references list (ui/references.slint) reached main after the build used here; on main at 2c64f0229 its selected row uses the same palette ink over the same fill, so it has the same black-on-blue text in dark and the same change applies. It is not captured: the prototype base predates it, and showing it needs a running language server.

The opened file fixture.ts is the selected row at start; the source has focus.

Selected result in the combined search

Shift twice, then type fixture; the first result is selected.

Options

A: Keep the palette's selection ink (current main)

The current main build: black on the blue fill in dark, white in light.

Pros

  • Follows the toolkit palette with no override, so it tracks future palette changes.
  • By the WCAG 2 ratio, black on this blue is marginally higher than white (4.64 against 4.53).

Cons

  • By APCA, black on this blue is weak: Lc 33.4, against Lc -76.2 for white (both figures from doc/handover/slint-ide-0x.md).
  • In dark, selected rows look different from selected source text, which is already white on the same fill.

Build: main a630b237b.

B: White ink on the selection fill in both schemes

The tree and the search list use white for selected-row text instead of the palette's selection ink.

Pros

  • Stronger perceived contrast in dark (APCA Lc -76.2 against 33.4) and still above 4.5 by WCAG 2 (4.53).
  • Selected rows match selected source text, and the light scheme does not change at all.

Cons

  • A fixed white that ignores the palette: if the selection fill ever changes (for example with a system accent color), the ink must be rechosen, as the source view already does from the fill.
  • Does not reach selected text inside the toolkit inputs, which stays black on blue in dark (see question 3: the custom input of option B could set it; the toolkit LineEdit does not expose it).

Build: commit c1e3a8d2f on prototype/ide-ui-variants.

Ranking

Ranking: B > A

  • B over A: B makes dark selected rows clearly more legible by APCA at a WCAG 2 cost of 0.11, and brings rows in line with the source view; A's only advantage is having no override.

How these frames were made

  • Each option is one commit on the branch prototype/ide-ui-variants; its tree is main a630b237b plus only that option, so checking the commit out builds that option alone. package/ide/app/design/README.md lists the commits.
  • Every frame comes from mise run //package/ide/app:inspect:native <scheme> scroll, with IDE_NATIVE_MCP_PORT=9378 (dark) or 9379 (light), a fresh session per question, scheme, and option, and the default 1100 by 660 nested screen at scale 1.
  • Each session adds the same four entries to its disposable project before any frame: src/index.ts, README.md, package.json, and an-extremely-long-file-name-that-reaches-the-divider.ts. The tree order is asserted in every session. The file label at the top shows that session's random temporary directory, so it differs between frames.
  • Keys and clicks are seat input through the compositor control socket. Hover uses Slint MCP move_pointer, because the control protocol has no plain pointer move: its zero-notch wheel moved the pointer but left hover off on the divider in a control run.
  • A frame is saved once two screenshots 250 ms apart are identical. Frames with a focused text input are chosen from 12 samples 120 ms apart, keeping the settled sample with the caret drawn, so every option shows the caret in the same blink phase.

What these frames cannot show

  • The mouse cursor is not in the frames: the compositor screenshot holds the app surface only, so the column-resize cursor that every divider option shows on hover is not visible.
  • Drags are not shown. The compositor protocol has no held-button drag; the drag states (full ink, and the larger handle in divider option D) exist in the prototypes but were not captured.
  • The clear-icon option B input is a visual prototype: it reproduces the fluent look, selection, caret scrolling, and placeholder, but not the toolkit's right-click menu (cut, copy, paste, select all), and input-method preedit was not exercised.
  • Screen-reader behavior is not shown. The divider keeps its slider role and its increment, decrement, and set-value actions in every option.
  • The references list is not shown. It reached main after the prototype base, and showing it needs a running language server; question 5 says how the same choice applies to it.
